你问一个模型：“公司报销差旅费的标准是什么？”模型可能答得很流畅，却把去年的规定当成今年的，甚至编出一个不存在的金额。问题不一定是模型不够聪明，而是它没有拿到**当前、正确、属于你有权限看的资料**。

RAG 是 *Retrieval-Augmented Generation*，可以理解成“先找资料，再让模型结合资料回答”。但真正可用的 RAG，远不止“把 PDF 切成几段，存到向量库，再取前三段”。今天常见的系统会按问题类型，组合关键词检索、语义检索、重排、数据库查询和多轮检索；同时把权限、时间、引用和评测放进同一条链路。

下面用一个企业知识助手的例子，拆开这几种做法。

先看它们通常用在哪里。企业内部助手和客服知识库要回答“现行规则是什么”；研发助手要从代码、接口文档和故障记录里找依据；研究助手则常常要汇总多份报告。它们都叫 RAG，但资料的更新速度、权限边界和“答对”的标准并不一样。客服更在意答案能否稳定复现，研发助手需要精确到版本与代码位置，研究助手还要处理来源之间的分歧。

## 第一种：固定流程的文档问答

最容易落地的是两步式 RAG：

```text
用户提问 → 检索相关文档 → 把片段交给模型 → 带引用地回答
```

适合“制度在哪里写着”“某个接口参数是什么意思”这类问题。它的步骤固定，延迟和费用比较好估算，也方便定位错误：检索不到，还是模型没用好检索结果？

做一个最小系统时，别急着选模型。先处理资料：抽取文本、按标题或自然段切块、保存文档 ID、标题、页码、更新时间和权限范围。切块太大，检索结果会塞满无关内容；太小，又可能丢掉“这段规定适用于哪个部门”这样的上下文。一个可行的起点是按小节切，再让片段保留所属标题和原文位置，而不是机械地每隔固定字符切一刀。

回答时，给模型一个明确规则：**只根据检索到的资料作答；资料不足时说不知道，并给出已找到的来源。** 这能减少无依据的回答，但不能替代程序层面的权限检查和结果验证。

## 第二种：关键词和语义一起找

“向量检索”擅长找意思相近的句子。用户说“出差住酒店能报多少”，它有机会找到写着“住宿费标准”的制度。但它也可能把两个相似地区、不同年份的标准混在一起。关键词检索在精确编号、产品型号、文件名和专有名词上常常更稳。

所以很多应用会使用**混合检索**：同一个问题同时走关键词与向量两条路，再合并候选结果。比如“2026 年广州出差住宿费上限”，关键词能抓住年份和城市，语义检索能抓住“住宿费”和“酒店报销”其实在问同一件事。

合并不意味着把两个结果列表直接拼起来。两种检索的分数通常不能直接比较，常用的办法之一是按排序名次融合，例如 RRF；接着可用重排模型对候选片段重新排序。重排的工作是“在已经找来的几十段里挑最相关的几段”，代价是多一次模型或服务调用，因此要看它带来的准确率提升是否值得增加的延迟。

更关键的一步往往是**元数据过滤**。如果用户只被允许查看华南区资料，检索时就先限制权限和地区，再谈相似度。把全公司文档都检索出来，最后让模型“不要泄露”，边界已经放错了。

## 第三种：先理解问题，再决定查什么

不是所有问题都适合查文档。问“最新报销制度怎么规定”，该查正式制度；问“我上个月报销了多少”，该查用户自己的交易记录；问“为什么这笔报销被退回”，可能需要把制度和流程记录合起来看。

这时应用可以先做一个轻量路由：

| 问题 | 更合适的数据源 | 为什么 |
| --- | --- | --- |
| “差旅住宿标准是什么？” | 制度文档 | 答案在段落里，需引用版本和章节 |
| “我今年累计报销多少钱？” | 结构化数据库 | 需要精确汇总和用户权限，不能靠文本相似度猜 |
| “这笔报销为什么被驳回？” | 流程记录 + 制度文档 | 要核对具体记录和适用规则 |

这里容易犯的错，是把数据库表也转成一堆文本块，指望向量搜索给出精确金额。结构化数据应由可靠的查询接口返回，再由模型解释结果。让模型直接生成任意 SQL 也有风险：至少要限制可访问表、字段、查询范围和执行时间，重要写操作不能从问答链路里顺手开放。

## 第四种：Agent 式 RAG，适合复杂问题

固定流程每次只检索一次。有些问题需要追问：“2024 年和 2026 年的住宿标准有哪些变化？对这笔申请有什么影响？”系统可能要先找两个版本，再找适用地区，再查申请记录，最后对照差异。

Agent 式 RAG 让模型在受限工具列表里决定下一步：查哪个资料库、要不要改写搜索词、是否继续检索。它适合研究型或跨数据源问题，但步骤数不固定，延迟、成本和错误路径也更多。一个稳妥的设计是：先用固定流程覆盖多数常见问题，只有在证据不足或问题确实需要跨源推理时，才进入多步检索。

即便用了 Agent，也不要让模型自己决定“有没有权限”。工具必须在执行前校验用户身份和数据范围；每轮检索应有次数、时间和结果量上限。否则它可能一直换词搜索，却没有更接近答案。

## 联网、图谱和多模态：按资料的形状选工具

以上四种做法并不是互斥的产品类别。它们解决的是检索流程的问题；联网、图谱和多模态处理的是**资料从哪里来、长什么样**。

| 资料与问题 | 可考虑的做法 | 要特别检查的地方 |
| --- | --- | --- |
| 新闻、公告、价格等变化快的信息 | 联网检索，保留抓取时间和原始链接 | 网页可信度、发布日期、转载与原文是否一致 |
| 合同、论文、说明书中的图表 | 解析版面、表格和图片，再把文字与图片证据关联起来 | 单位、行列对应关系、图注是否抽取正确 |
| “某服务依赖哪些系统，变更影响谁” | 从可靠数据中建立实体关系，再结合文档检索 | 关系是否过期，边的来源能否追溯 |
| 资料很少且上下文能放入模型 | 直接提供完整资料，或做简单筛选后提供 | 长上下文里的关键信息是否被忽略，成本是否可接受 |

所谓 *GraphRAG*，通常是在检索中引入实体与关系，让系统能沿着“服务 → 依赖 → 负责人”这样的连接找证据。它适合关系问题，却不意味着所有文档都要先建知识图谱：关系抽取和维护本身会出错，也会增加更新成本。只有当普通段落检索反复漏掉跨文档关系时，它才值得进入评测。

多模态 RAG 也是类似道理。一份报销标准如果写在表格里，纯文本抽取可能把“广州”和“北京”的金额串行；这时先保留表格结构，必要时让模型查看对应页面图片，比盲目扩大向量库更直接。无论用哪种模型，最后都要能定位到原文件和具体页码。

联网检索尤其要注意“新”不等于“对”。搜索结果可能是转载、旧页面、广告，甚至包含试图指挥模型的恶意文字。外部内容只能作为待核对的证据，不能当作系统指令；关键结论应优先核对官方来源与发布时间。

## 走一遍真实请求

假设员工问：“我在 2026 年去广州出差，住了两晚，每晚 520 元，能全额报销吗？”一条可审计的链路可以这样设计：

1. **识别身份与问题**：取得员工部门、出差日期与目的地；先确认“520 元”是含税单价还是总额。信息缺失就追问。
2. **限定可检索范围**：只查该员工可见、在出差日期生效的差旅制度。旧版制度可以用于解释变化，但不能偷偷当作现行依据。
3. **找候选证据**：用“广州”“住宿费”“2026”等词做关键词检索，同时用语义检索覆盖“酒店费用”“住宿标准”等说法；合并、重排后保留适用条件所在的小节。
4. **计算并回答**：从制度读出城市、职级与限额，再用程序计算两晚的可报销金额。模型负责解释规则和列出依据，不负责凭感觉算账。
5. **校验与留痕**：检查答案中的金额、日期和引用是否与证据一致；记录命中的文档版本与检索耗时，方便后续排查。

如果没有找到职级信息，系统应该说明还缺什么，而不是随便选一个标准。这个例子也说明：**RAG 不等于把所有步骤交给模型**。检索、权限、计算和引用各有更可靠的实现方式。

## 检索质量，常败在数据而不是模型

系统答错时，先检查下面几件事：

1. **文档版本**：旧制度是否还混在索引里？检索结果有没有生效时间？
2. **切块边界**：正文和适用条件是否被切到了不同块？表格是否抽取错列？
3. **更新链路**：原文件修改后，索引是否重建？删除的文件是否仍可检索？
4. **权限范围**：文档 ACL 是否同步到检索层？权限变更后旧索引是否立即失效？
5. **引用位置**：结果能否指向文档、章节、页码，而不是只显示“来源：某 PDF”？

“给每块加一句它来自哪里、讲什么”这一类上下文增强有时能改善检索，尤其是原始块太短、单独看不出主题的时候。但它也增加建索引成本，并可能带来自动生成上下文的错误。先用真实问题评测，再决定是否使用。

## 怎么评测，才知道改动真的有效

不要只挑三道演示题看模型回答是否流畅。准备一组来自实际使用的测试问题，每题至少标注：允许访问的数据范围、正确证据、预期答案或可接受的拒答条件。然后分两层评估：

- **检索层**：正确证据有没有进入前几条结果？错误版本是否被排除？可用 Recall@K、MRR 等指标辅助观察，但要同时看具体失败样本。
- **回答层**：结论能否被引用支撑？是否引用了错页？资料不足时会不会编造？数字、日期和适用条件有没有对错？

还要记录 P95 延迟、每次请求的模型与重排成本、检索失败率和用户反馈。混合检索加重排可能让答案更准，但如果 P95 从两秒涨到十秒，就要看场景是否接受。比较方案时，尽量固定同一批问题、文档版本和权限条件。

上线前，可以专门放入几类“容易出错的题”：不存在的政策、过期制度、同名不同部门文件、无权限的文档，以及答案分散在多个来源中的问题。一个敢于说“资料不足”的系统，通常比一个每题都能编出答案的系统更有用。

## 一条实用的建设顺序

我会按这个顺序做：先选一个边界明确的知识库，做带来源的固定流程 RAG；用真实问题找出检索失败；再加关键词与向量混合、元数据过滤和必要的重排；涉及金额等精确数据时接入受限查询工具；最后才考虑让 Agent 自主安排多步检索。

RAG 的关键不在于“用了哪种向量库”，而在于**每个回答能不能找到正确、当前、获授权的证据**。只要把这一点当作设计和评测的中心，系统就更容易从演示走向真正可用。

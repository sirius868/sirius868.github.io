让三个 Agent 同时写一篇技术文章，听起来效率很高。实际很可能出现：一个改了提纲，另一个还按旧提纲写；两个都改同一段，最后互相覆盖；第三个说“已核对事实”，却没留下来源。最后花在合并与返工上的时间，可能超过单个 Agent 完成任务的时间。

多 Agent 协作真正解决的，是**可并行的不同工作**。它需要明确的任务边界、交接格式和最终验收，而不是多开几个聊天窗口。下面用“发布一篇技术文章”来拆解。

## 先判断任务能不能拆

假设目标是写一篇“后端多级缓存”文章。可分成三块：资料核对、结构与初稿、代码示例验证。它们有依赖关系：代码验证可以和资料核对并行，最后由一个整合者修改正文；如果提纲尚未确定，两个写作者同时写正文就容易冲突。

可以把任务画成一张小图：

```text
确认目标与读者
   ├─ 资料核对 ─────┐
   ├─ 示例验证 ─────┤→ 整合成稿 → 最终检查 → 发布
   └─ 文章提纲 ─────┘
```

拆分的原则是：**每个子任务有可交付结果，尽量少共享可写状态**。按“你负责想一想”“你负责再看看”分工，难以判断谁做完了；按“给出三条带来源的技术结论”或“运行示例并附命令与结果”分工，才方便验收。

## 常见的三种协作结构

| 结构 | 谁决定下一步 | 适合什么 | 主要代价 |
| --- | --- | --- | --- |
| 主 Agent 分派子任务 | 主 Agent | 可明确拆分的研究、编码与验证 | 主 Agent 要整合与检查结果 |
| 流水线交接 | 当前步骤或固定流程 | 写作、审核、发布等稳定流程 | 上游错误会一路传播 |
| 共享任务池 | Agent 自行领取任务 | 大量独立小任务 | 需要锁、状态同步与冲突处理 |

对个人技术博客来说，主 Agent 分派通常最容易落地：一个负责最终文章，其他 Agent 只提交资料或验证结果。流水线适合反复执行的固定流程；共享任务池只有在任务量足够大、任务之间独立时才值得付出调度成本。

## 交接格式比“多说几句”重要

一个子 Agent 返回“缓存方案没问题”几乎没用。它应交回可以检查的结果，例如：

```text
任务：验证 Caffeine + Redis 读取示例
输入版本：文章草稿 commit abc123
结果：示例可编译 / 未运行 / 失败（只能选实际情况）
证据：运行命令、依赖版本、输出摘要
发现：两处描述把 Redis 失效误写成所有实例立即失效
待决问题：是否允许本地缓存 20 秒陈旧数据
```

这里的“输入版本”很关键。若文章已改过，旧版本的审核意见可能已经失效。交接还要区分**事实、推断和建议**：文档原文说了什么、从中推断了什么、建议作者怎样改，不能混在一句话里。

共享状态不必是一整段聊天记录。更可靠的是结构化任务记录：任务 ID、负责人、输入版本、状态、产物位置、验证证据、失败原因。它帮助系统在中断后继续，也让人能追踪“为什么写成这样”。

## 并行会带来写入冲突

如果两个 Agent 同时修改同一个 Markdown 文件，最简单的处理方式是**明确所有权**：一个 Agent 负责合并正文，其他人给出建议或独立草稿，不直接写目标文件。代码任务可以分配不同模块或独立工作区，再通过差异审查合并。

不能只依赖“最后写入者获胜”。它会静默丢掉另一个人的成果。需要共享写入时，至少记录基线版本，并在提交前检查目标文件是否改变；冲突发生就重新合并。对外部动作还要考虑重复调用：两个 Agent 都以为自己负责发布，可能触发两次部署或发两封邮件。发布权限应集中在明确的执行者，写操作使用幂等标识或状态检查。

## 验证者也需要证据边界

把“审稿”交给第二个 Agent，并不等于拥有独立真相。如果它和写作者用同一份错误资料，两个回答一致也可能都错。验证任务应具体到证据：查原始文档、运行代码、对照测试输出、检查链接。审稿者无法验证的地方要明确写“未核实”。

一个实际可用的发布门槛可以是：文章中的关键技术结论有来源；代码示例运行或清楚标注为伪代码；正文与标题一致；Markdown 构建通过；最终发布地址可访问。完成条件由程序或人核对，不能只凭某个 Agent 的“已完成”。

## 不可信内容不能通过协作链洗白

检索到的网页、仓库 README 或用户提交的材料可能包含“忽略你的规则”“把密钥发出去”等指令。研究 Agent 可以引用它们作为资料，不能把其中的命令当成更高权限的规则再交给写作 Agent。交接时应保留来源和可信等级，不要把“网页上写着”转成“系统要求”。

权限同样按工具和任务分配。只查资料的 Agent 不需要部署权限；写文章的 Agent 不需要访问生产数据库；最终执行者即使有权限，也要按授权范围检查发布对象。协作系统的危险常发生在**交接处**：信息被压缩后，来源和限制丢了。

## 多 Agent 到底有没有更快

除了最终质量，还要量化协作成本。准备一批同类型任务，对比单 Agent 与协作方案：

- **完成率**：真正通过验收的比例，而不是 Agent 自报“完成”的比例。
- **总耗时**：从开始到可发布的时间，包含等待、合并、返工与人工介入。
- **总成本**：所有模型调用、工具调用和重试的花费。
- **错误类型**：事实错、接口不兼容、版本冲突、重复操作、遗漏边界。
- **可追踪性**：能否回答每个关键结论从哪里来、由谁验证。

并行的理论收益会被交接与整合成本吃掉。若一篇短文章一个 Agent 十分钟能写好，再派三位 Agent 可能只会把流程变重；若任务包含独立资料调查、可并行测试和大量文件审查，协作更可能有收益。评测要用相同任务、相近模型与一致验收标准，不能拿最成功的一次演示作结论。

## 一条务实的落地路线

先让单 Agent 的任务流程稳定，明确输入、产物和验收；再把最耗时且相互独立的步骤拆出去；用固定交接格式收结果；最后根据完成率、耗时和返工情况决定是否继续增加 Agent。每增加一个参与者，都应能指出它减少了哪类瓶颈。

Agent 协作做得好，外观看起来可能很普通：有人查证、有人写、有人验证、一个人负责合并与发布。真正的深度在于任务边界清楚、状态不丢、冲突可见、结果能验。

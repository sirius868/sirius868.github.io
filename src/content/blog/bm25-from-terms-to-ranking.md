假设你在公司文档里搜“广州住宿费标准”。有的文档只出现一次“住宿费”，却正好是最新制度；有的文档把“住宿费”重复了二十次，却是去年的培训材料。按关键词出现次数排序，后者很可能排到前面。BM25 要解决的就是这个问题：**一个词出现多少次、这个词有多稀有、文档有多长，应该怎样共同影响相关性。**

它是经典的词项检索排序方法，今天仍常用于站内搜索和 RAG 的候选召回。先把它当成一个“给查询和文档打匹配分”的公式，再看公式背后的取舍。

## 先建立一个最小搜索过程

检索系统通常先把文档和查询拆成词项，建立倒排索引。例如查询“广州住宿费标准”可能拆成“广州 / 住宿费 / 标准”；倒排索引能快速找到含这些词的文档。BM25 再给候选文档打分，排到前面的文档更值得交给读者或后续重排模型。

这一步有两个重要前提。第一，**分词决定什么才算同一个词**：“酒店报销”和“住宿费”若没有共享词项，纯 BM25 未必能匹配。第二，BM25 只知道词项与统计量，不知道制度是否过期，也不知道用户有没有权限看文档；这些需要在检索流程中另行处理。

## 公式看起来复杂，其实只有三个问题

常见的 BM25 形式可以写成：

```text
score(q, d) = Σ IDF(t) × [ f(t,d) × (k₁ + 1) ]
                       / [ f(t,d) + k₁ × (1 - b + b × |d| / avgdl) ]
              t ∈ q
```

这里 `q` 是查询，`d` 是文档，`t` 是查询中的词；`f(t,d)` 是词在文档里的出现次数，`|d|` 是文档长度，`avgdl` 是索引中平均文档长度。`k₁` 控制词频增加时分数增长得多快，`b` 控制长度归一化的强弱。常见起点是 `k₁=1.2`、`b=0.75`，但它们不是普适最优值。

用人话说，公式在问：

1. **这个词有多能区分文档？** 几乎所有文档都写“公司”，它的区分力低；只有少数文档写“住宿费”，区分力高。这由 IDF 表示。
2. **它在当前文档里出现了几次？** 出现两次通常比一次更有信号，但二十次不该比两次强十倍。这是词频饱和。
3. **文档是不是特别长？** 一本手册碰巧包含很多查询词，不一定比一页精确说明更相关。长度归一化会调整这个偏差。

IDF 的具体计算有不同版本。很多实现使用类似 `log(1 + (N - df + 0.5) / (df + 0.5))` 的平滑形式，其中 `N` 是文档总数，`df` 是包含该词的文档数。上面的 `Σ` 是便于理解的写法：多个查询词通常分别贡献分数；查询词重复出现时，具体怎样处理还取决于搜索引擎实现与查询构造。不要把网上某一条公式直接当作 Elasticsearch、Lucene 或其他搜索引擎的完全相同实现：版本、字段统计、分词器和参数都会影响实际分数。

## 为什么重复一百次也不能稳赢

假设两篇长度相近的文档都包含“住宿费”。A 出现 1 次，B 出现 10 次。`k₁=1.2`、暂不考虑长度差时，词频因子分别约为 `1` 和 `1.96`。B 的确更高，却不到 A 的两倍。这就是饱和：词出现得越多，新增一次带来的收益越小。

如果把词频直接乘到分数上，页面堆满关键词就容易赢。BM25 不会彻底解决关键词堆砌，但至少避免“出现十次就必然得十分”的线性增长。`k₁` 越大，增长越接近线性；越小，越快饱和。它影响的是**词频的权重曲线**，不是“结果有多聪明”。

## 长度归一化也可能帮倒忙

长文档有更多机会碰巧包含关键词。`b=0` 时不按长度调整；`b=1` 时按文档长度与平均长度充分调整。对新闻正文、产品描述这类长度差异明显的内容，长度归一化常有帮助。

但如果索引里混着标题和整本手册，或者把一份手册切成大小差异很大的块，分数解释会变复杂。一个精准但短小的标题可能被推得很高，长文档里真正有用的小节却被压低。工程上常把**标题、摘要、正文分成不同字段**，对标题设置更高权重，或把长文档按语义章节切块，而不是只调 `b` 试图解决所有问题。

## 中文搜索的第一道关是分词

英文有空格，中文没有天然的词边界。“上海市差旅住宿费标准”可以切成“上海市 / 差旅 / 住宿费 / 标准”，也可能被错误切成“上海 / 市差 / 旅住 / 宿费”。后一种切法会直接破坏匹配。

所以在调 BM25 参数之前，先做三件事：

- 用真实查询检查分词结果，特别是产品名、缩写、人名、错误码和数字型号。
- 为领域词建立词典或同义词规则，例如“酒店费用”和“住宿费”；同义词要谨慎，别把含义不同的词硬并在一起。
- 保留精确字段用于编号和文件名查询。像 `ERR-1042`、订单号、SKU 型号，分词后再搜可能比精确匹配更差。

中文分词器的选择往往比把 `k₁` 从 1.2 调到 1.4 更能改变结果。分词、索引和查询端的处理还要保持一致，否则文档里有词，查询却匹配不上。

## 放进 RAG 时，BM25 负责哪一段

用户问“广州酒店最多报多少”，正式制度写的是“广州市住宿费限额”。BM25 可能命中城市和费用类词，但“酒店”与“住宿费”的表达差异会影响召回。向量检索更容易跨用词找相近语义，却可能混淆地区、年份或编号。实际系统常让两条路并行：

```text
查询 → 权限/时间过滤 → BM25 与向量检索 → 合并候选 → 重排 → 引用证据回答
```

两路原始分数通常不可直接相加，因为量纲和分布不同。可以先用按排名融合的方法，例如 RRF；随后让重排模型仔细比较候选片段。BM25 在这里是一位擅长**精确词项**的召回员，特别适合编号、专有名词和用户明确写出的关键词。

要注意过滤的顺序：权限、地区和生效日期最好在检索阶段约束，不能检索完全部资料后让生成模型“自行忽略”。BM25 排序再好，也不会修复错版本或越权候选。

## 怎么判断调优真的有用

准备真实查询集，每题标注可接受的相关文档与版本。先看 `Recall@K`：正确证据有没有进入候选前 K 条；再看 `MRR` 或 `NDCG`：相关文档是否排得足够靠前。指标之外还应逐条读失败样本，区分分词失败、索引缺失、字段权重不合理和文档本身过期。

可以按这条顺序改进：先修数据和分词，再定字段与切块，接着比较 BM25 参数，最后评估是否需要向量检索与重排。每次只改一类因素，在同一批查询和同一版索引上比较。否则看到分数上涨，却不知道是谁起了作用。

BM25 的价值并不是“老算法也能打败新模型”。它把词项匹配做得可解释、便宜、稳定；和语义检索搭配时，还能补上后者对精确实体不够敏感的短板。真正可靠的搜索系统，需要让**词、数据版本和业务边界**一起工作。

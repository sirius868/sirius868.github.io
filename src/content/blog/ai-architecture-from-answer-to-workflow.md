用户问：“我的耳机晚到了三天，还坏了，能不能换？”一个聊天模型也许能写出一段很像客服的回答。但如果系统还要查订单、核对当前政策、登记申请，问题就从“怎样生成一句话”变成了“怎样让一句话背后的事实和动作都站得住”。

这篇文章讨论的是**应用层的 AI 架构**：把模型放进真实业务时，信息从哪里来，谁有权决定，失败后怎样继续，以及如何知道系统真的变好了。它不依赖某个模型或框架。下面一直用这个售后请求作例子。

## 先把请求分成三种工作

同一句用户输入，可能包含三种性质完全不同的工作：

1. **解释**：“换货政策是什么？”需要找到适用的政策、说明条件并给出来源。
2. **判断**：“我的订单符合吗？”需要读取本人订单，按确定的业务规则核对型号、日期和状态。
3. **执行**：“帮我提交申请。”会改变系统状态，需要独立确认、权限检查和可靠写入。

如果让模型一次性完成这三件事，回答看起来顺畅，责任边界却会消失。模型可能把旧政策说成新政策，或把“建议可以申请”说成“已经提交成功”。架构的第一步，是让不同工作走不同路径；**不是每个问题都需要一个会自主调用工具的 Agent**。固定问答可以走检索流程，资格判断可以走业务服务，真正的多步任务才需要状态机或受约束的 Agent。

```text
用户请求
  ↓
身份与意图识别 ──→ 简单说明：检索资料 → 带来源回答
  │
  ├────────────→ 资格核对：读取本人订单 → 业务规则 → 解释结论
  │
  └────────────→ 申请办理：核对 → 方案 → 用户确认 → 事务写入
                              ↑                      ↓
                              └──── 状态与恢复 ──────┘
```

这里的“意图识别”只是路由建议，不能因为模型说“用户已授权”就跳过鉴权。真实身份和操作权限始终由服务端会话及业务数据确定。

## 知识层：先决定什么算事实

RAG 常被说成“检索几段文字，再交给模型”。在售后场景里，真正困难的是找到**当前有效、适用于这个型号、允许这个用户看到**的那一段。若先从所有文档里取相似度最高的五段，再让模型猜版本，旧条款很容易混进答案。

一种更稳的顺序是：先按权限、商品型号、生效时间和政策状态缩小候选范围；再用关键词或向量检索找相关段落；必要时重排；最后把原文、版本和来源位置交给模型。结构化事实如订单状态、支付金额，不应从政策 PDF 里猜，而应查询对应的业务系统。

```text
可见范围与有效版本 → 候选检索 → 可选重排 → 证据片段与来源
本人订单数据库 ────────────────────────→ 结构化事实
```

检索分数只表示“可能相关”，不表示政策已经适用；引用链接只表示“答案有出处”，不表示推理一定正确。若证据相互冲突，系统应指出冲突并停止自动判断，而不是让模型选一段最顺口的。资料被更新或撤回后，还要能解释历史决定当时依据的是哪个版本。

## 模型层：让输出成为提案

模型擅长把自然语言整理成结构、归纳材料、解释规则。但它对外部状态没有天然的权威。可以让它输出“用户报告故障、希望换货、还缺购买日期”，并附上使用了哪些证据；不能把它输出的 `eligible: true` 直接当成资格判定。

一个实用的接口契约可以把输出拆成三部分：

```json
{
  "extracted_facts": { "issue": "故障", "requested_action": "换货" },
  "evidence_ids": ["policy-2026-v3#exchange", "order-123"],
  "proposed_reply": "我先核对订单和适用条款，再告诉你能否申请。"
}
```

程序必须校验结构、字段长度、来源是否真的存在且可访问。随后由业务规则计算资格。模型版本、提示词版本和工具契约也应记录在任务轨迹里，否则一次结果变化很难归因。更大的模型通常改善某些模糊输入，却不一定修复过期政策或越权读取；后两者首先是数据与权限问题。

## 执行层：确认、幂等和恢复各管一件事

现在假设系统已经提出方案：“为这张订单登记换货申请。”用户点击确认前，方案至少应包含订单、动作、关键条件和版本。用户确认的是**这个具体方案**。如果订单状态或政策在确认后变化，旧确认就失效，系统要重新核对并展示新方案。

写入时最常见的麻烦不是模型突然说错，而是网络超时：客户端不知道提交是否成功，于是又点一次。为每次业务操作生成稳定的操作键，在数据库事务中写入，并用唯一约束防重；重试同一操作键时返回已创建的工单。状态机或 LangGraph checkpoint 负责记住任务走到哪里，**不能替代数据库的事务和唯一约束**。一个负责恢复流程，一个负责避免重复副作用。

若登记后还要通知客服，通知可以通过事务外盒等机制异步投递，避免“工单已入库但通知失败”被误说成“登记失败”。页面应清楚区分“申请已记录”“等待人工办理”和“办理已完成”。这些状态是业务事实，不是模型文案。

## 评测层：分层看错误，别只问答得像不像

一套 AI 系统至少要分开测四件事：

| 层次 | 应检查什么 | 典型错误 |
| --- | --- | --- |
| 检索 | 适用证据是否进入候选、版本和权限是否正确 | 找到旧政策或别人的订单 |
| 生成 | 回答是否忠于证据、能否承认未知 | 引用正确却推断过头 |
| 流程 | 缺信息、政策变更、人工接管时是否走对路径 | 跳过重新确认 |
| 写入 | 超时、重试、并发下最终状态是否正确 | 一次确认生成两张工单 |

只看一组问答的“答案正确率”，很难知道改进该落在哪层。可以从少量人工标注的真实问题开始，保存问题、可用资料版本、预期操作与最终状态；每次调整检索、提示词或模型，只比较同一组输入，并补充新发现的错例。指标也要标明样本范围：小型合成集上的 Recall@5，不能写成线上用户满意度。

运行时记录一条请求的路由、证据版本、模型与工具调用、耗时、失败阶段和最终业务状态，才有办法定位问题。日志应避免存放密钥和不必要的个人信息。对于会改变外部状态的路径，最终数据库状态比“模型说已完成”更值得信任。

## 成本与延迟也是架构约束

一条请求若经历查询、重排、三次模型调用和两次工具调用，用户感受到的是总耗时，不是单次模型的速度。可以把请求粗略拆成：

```text
总耗时 ≈ 路由 + 检索 + 模型 + 工具等待 + 排队与重试
```

先测每一段，再决定优化。常见做法是让简单问题走固定流程、缓存可复用的公开资料、限制传给模型的证据长度；对复杂请求设置总时间、步骤和费用预算。外部服务拥堵时，队列长度和并发上限比盲目重试更重要。降级可以是只展示已核实资料并请人工处理，而不是让模型在证据不足时继续猜。

## 怎样逐步做出来

先做一条窄而完整的链路：只回答一个政策问题，带有效来源；然后接入本人订单并用规则判断；再加入确认与幂等写入；最后才让模型在受限工具内选择下一步。每加一层，都补相应的失败样例和可观察状态。

判断 AI 架构是否成熟，不看图上有多少方框，而看一个具体请求能否回答五个问题：**事实来自哪里？谁作决定？谁能执行？失败后怎样恢复？结果如何验证？** 这五个问题有清楚答案，模型才真正成为系统的一部分。

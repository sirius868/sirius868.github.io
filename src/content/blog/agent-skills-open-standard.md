10 月 22 日，Anthropic 宣布把 Agent Skills 标准捐赠给 Linux Foundation 旗下的 Agentic AI Foundation（AAIF）。官方描述中，一项 Skill 可以是包含 `SKILL.md` 的文件夹，旁边还可以放脚本和参考资料。它把某件事该怎么做，写成 Agent 能读取的操作说明。官方同时称，已有超过 70 个 Agent 平台集成该标准；这是发布方的统计口径，不能直接理解成每个平台都能运行同一份 Skill、得到相同结果。

这条消息值得关注，并非因为多了一个 Markdown 文件格式，而是它碰到了 Agent 产品的一个实际问题：**模型会说“我能做”，但常常不知道某个团队具体要求怎样做。** 比如“发布一篇博客”，在不同项目里可能意味着写 frontmatter、更新翻译、检查草稿状态、构建站点，最后再部署。通用模型知道博客是什么，却不知道这个项目的精确流程。

## Skill 到底是什么

可以把 Skill 理解成“可随项目分发的操作手册”。一份最简单的 Skill 会交代适用场景、输入与输出、操作顺序、需要读取的资料，以及错误时该怎么处理。它还可能附带模板或脚本，让 Agent 少凭空猜命令。

```text
技能目录/
├─ SKILL.md          # 什么时候用、按什么步骤做
├─ references/       # 规则和示例
└─ scripts/          # 可复用的辅助程序
```

这样的文件有一个朴素的优点：人也能读。团队可以像审查代码一样审查流程，修改内容也能进入版本控制。如果换一个支持相同约定的 Agent，至少不必从零口述团队规矩。

但“能读取”只是第一层兼容。不同产品的工具名称、权限模型、上下文窗口和执行环境可能不同。一个 Skill 写了“运行测试”，不能保证所有 Agent 都拥有终端，也不能保证它们知道应该先启动哪个数据库。**格式可移植，不等于执行结果可移植。**

## 它和 MCP、普通提示词有什么不同

三者经常同时出现，却回答不同问题：

| 方式 | 主要回答的问题 | 例子 |
| --- | --- | --- |
| 提示词 | 这次对话希望模型怎样回答？ | “请用通俗中文解释错误。” |
| Skill | 这类任务在本项目里怎样完成？ | “写文章后检查日期、翻译和构建。” |
| 工具协议（如 MCP） | Agent 能调用什么外部能力？ | “读取数据库中的文章列表。” |

Skill 可以告诉 Agent *何时*调用某个工具、怎样检查结果；工具协议负责提供可调用的接口。前者偏流程，后者偏连接。两者都不能单独赋予业务权限：即使说明书写着“提交发布”，服务端仍应验证调用者和目标资源。

## 中立治理会带来什么

Anthropic 的公告说，AAIF 将接收标准名称、标识、GitHub 组织和域名，并由来自不同公司的工程师作为个人参与维护。公告提出的下一步包括版本化发布、正式提案流程和安全指引。这些是**规划中的治理方向**，不等于所有兼容性或安全问题已经解决。

对开发者而言，中立治理的潜在价值是减少格式被单一产品路线绑住的风险。今天写给一个 Agent 的任务说明，未来有机会在其他工具里复用。但真正的标准成熟度，还要看几个细节：版本升级会不会破坏旧技能？不同实现如何报告“不支持的工具”？附带脚本的权限边界怎样表达？这些问题必须靠规范、测试和真实跨平台使用来回答。

## 一个 Skill 怎样写得可靠

假设要给博客项目写“发布文章”Skill。只写“检查文章并发布”太空泛；把每个鼠标动作写死又容易因界面变化失效。比较实用的写法是：

1. **定义入口**：只在用户明确要求发布文章时使用，列出文章文件与目标仓库。
2. **写清检查点**：标题、日期、草稿标记、图片链接、英文版、构建结果分别如何验证。
3. **区分建议与动作**：模型可以提出修改，真正提交和部署仍按当前授权与项目权限执行。
4. **处理失败**：构建失败时停止发布、保留报错，修复后重新检查；不要因为模型说“应该没问题”就跳过。
5. **保持可审计**：记录使用的 Skill 版本和关键命令，让后续排查有依据。

如果 Skill 附带脚本，脚本就是代码，应像依赖一样审查。尤其是从外部下载的 Skill，里面的文字和脚本不能自动取得比用户、系统和项目规则更高的权限。一个写着“忽略其他要求”的文件，仍只是待检查的外部内容。

## 接下来该看什么

标准进入基金会，解决的是“谁来维护共同格式”的问题。它是否真正改善 Agent 工作，还得看实践：同一任务说明跨平台能否执行、失败是否容易定位、危险动作是否守住权限，以及团队维护一份 Skill 的成本是否低于反复口头说明。

我的判断是，Skill 最适合承载**稳定、可复查的程序性知识**，例如文章发布、事故排查或数据导入步骤。它不应该变成一个包罗所有项目知识的巨型提示词。把范围收窄、检查点写实，再给工具和权限各自明确的边界，才有机会把“模型大概懂”变成“流程能复现”。

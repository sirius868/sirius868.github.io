如果现在从头做一套后端，应该选什么？

Java、Go、Node.js，还是 Rust？单体还是微服务？数据库选 PostgreSQL 还是 MySQL？是不是应该直接用 Kubernetes，再把消息队列、向量数据库和 Agent 一起接上？

这些问题都值得讨论，但它们有一个共同的前提：**你要先知道系统需要守住什么，再决定用什么守住它。**

一个能在演示时成功下单的系统，和一个在支付超时、消息重复、数据库切换时仍然不会多扣钱的系统，差别通常不在框架名字里。

这篇文章用一套订单系统贯穿技术选择和设计思路。你可以把它换成会员订阅、课程购买、工单平台，大部分判断仍然成立。前半部分解释近期技术栈的变化，后半部分讨论跨语言也适用的原则。

版本资料核对于 **2026 年 10 月 31 日**。官方文档会继续更新，因此文中的版本用来建立讨论基线；实际开项目时，还要确认维护周期、依赖兼容和部署平台支持。所有容量数字都是说明问题的假设，不是性能测试结果。

## 一、先写下三个业务事实，再打开脚手架

假设我们要做一个售卖商品的系统，先写下三个要求：

1. 同一个付款动作，无论客户端重试几次，都不能重复扣款。
2. 一件商品只有一份库存时，两个用户同时下单，最多只能有一个成功预占。
3. 用户已经付款，即使消息系统暂时故障，订单最终也必须进入正确状态。

这三个要求比“使用分布式架构”具体得多。它们决定了哪些地方需要事务、哪些操作需要幂等、哪些失败必须被记录和补偿。

接着区分两类目标。

**正确性目标**规定什么绝对不能发生，例如库存不能被扣成负数、退款不能超过实付金额。它们要靠状态机、约束、事务和权限共同保证。

**服务目标**规定正常情况下服务应该有多好，例如订单接口每月成功率达到约定值、绝大多数请求在指定时间内完成。它们要靠容量、限流、监控和运维来实现。

响应非常快但偶尔多扣款，不是可靠；从不扣错钱但每天卡死几小时，也不是可靠。这两类目标需要分别设计。

一个实用的架构起点可以很简单：

```text
浏览器 / App
    │
    ▼
HTTP API → 业务模块 → 关系数据库
              │
              └→ 事务内写入待处理事件
                         │
                         ▼
                    后台任务 / 消息消费者

商品展示：按需要增加缓存
图片文件：对象存储
日志与指标：统一采集
```

先让事实存得对、失败查得到，再逐步加入更多组件。

## 二、当下技术栈的变化，应该怎样看

“最新”至少有四种意思：刚发布、仍在维护、能力更完整、适合当前团队。它们经常不是同一个版本。

下面是一套面向 Java 业务系统的候选基线，以及各自真正值得关心的内容。

| 层次 | 可以考虑的选择 | 应该研究什么 |
| --- | --- | --- |
| 运行时 | Java 25 LTS；已有项目也可评估继续使用仍受支持的 LTS | 虚拟线程、GC、容器资源识别、发行版维护策略 |
| 应用框架 | Spring Boot 4.x；旧项目按兼容情况迁移 | 依赖升级、HTTP 客户端、观测接入、测试和第三方库兼容 |
| 主数据库 | PostgreSQL 18，或团队熟悉且仍受维护的 MySQL | 数据约束、查询计划、锁、复制与恢复能力 |
| 缓存 | Caffeine、Redis，按访问模式选择层数 | 命中率、失效、一致性、回源保护 |
| 异步处理 | 先可靠的后台任务，必要时引入 RabbitMQ、Kafka 等 | 重复、顺序、积压、重试和消费进度 |
| 接口 | HTTP + OpenAPI；合适场景用 gRPC | 契约、兼容、超时、鉴权和错误语义 |
| 可观测性 | OpenTelemetry 与合适的指标、日志、链路存储 | 如何从用户失败追踪到具体依赖 |
| 交付 | 容器、自动化构建、托管运行平台；有需要再用 Kubernetes | 回滚、数据库变更、密钥、恢复演练 |

Oracle 的[支持路线图](https://www.oracle.com/java/technologies/java-se-support-roadmap.html)列出 Java 25 为 LTS 版本。LTS 表示长期支持路线，但具体支持期和许可仍取决于发行商，不能把某一家的商业政策套到所有 OpenJDK 发行版上。

核对时，[Spring Boot 系统要求](https://docs.spring.io/spring-boot/system-requirements.html)页面展示的是 4.1.2，最低要求 Java 17。这里建议了解 4.x 的能力，不代表已有 Spring Boot 3.x 项目必须立即跨大版本迁移。安全维护、生态兼容和迁移成本，同样是选型条件。

技术栈可以更新，选型的顺序应当稳定：先确认需求，再看团队能力和维护成本，最后比较候选工具。

## 三、Java 的一个重要变化：并发可以更自然，但资源仍然有限

传统 Java Web 服务通常让一个平台线程处理一个请求。线程请求数据库后，可能大部分时间都在等待网络，而不是执行计算。

当等待中的请求越来越多，平台线程的成本会变得明显。过去常见的解决办法之一是使用响应式编程，把等待表示为异步回调或数据流。

虚拟线程提供了另一条路：继续用比较直观的顺序代码处理大量等待型任务，由 JVM 调度大量虚拟线程到较少的平台线程上运行。

### 虚拟线程提高的是等待型并发的承载能力

[JEP 444](https://openjdk.org/jeps/444)在 JDK 21 正式引入虚拟线程。它特别强调：目标是提高高并发应用的吞吐能力，并不是让每一段计算自动变快。

比如生成一份报表需要压缩十万个文件，瓶颈是 CPU；把线程换成虚拟线程，并不会多出 CPU 核心。

反过来，如果一个请求需要等待数据库、对象存储和外部接口，虚拟线程可能让实现更自然，也能减少平台线程数量带来的限制。

在适用的 Spring Boot 应用中，可以通过以下配置启用相关支持：

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

这个开关并不意味着每个第三方库都会自动改变线程模型，也不意味着可以取消连接池、超时和并发上限。具体适用范围要看 [Spring Boot 官方说明](https://docs.spring.io/spring-boot/reference/features/spring-application.html)。

### 便宜的线程不能创造便宜的数据库连接

假设平均每秒有 2,000 个请求，平均每个请求在系统里停留 0.2 秒。按稳定系统中的 Little 定律估算：

```text
平均在途请求数 ≈ 平均吞吐量 × 平均停留时间
               ≈ 2,000 × 0.2
               ≈ 400
```

这里的 400 是平均在途请求数，不是应该配置 400 个数据库连接。请求不会全程占用数据库，而且数据库本身有承载上限。

如果数据库只适合同时处理 40 个重查询，让 4,000 个虚拟线程一起冲进去，只会把瓶颈从线程池搬到数据库连接队列。

因此，要给真正稀缺的资源设置边界：数据库连接池、外部支付接口的并发数、CPU 密集任务的执行数量。JEP 444 也明确建议不要为了限制并发而池化虚拟线程，应当用信号量等机制限制资源访问。

### 旧经验也需要更新

早期讨论虚拟线程时，经常会提到 `synchronized` 导致载体线程被固定占用，也就是 pinning。

[JEP 491](https://openjdk.org/jeps/491)在 JDK 24 改善了这一点，消除了绝大多数由 `synchronized` 引起的此类限制。到了新的 JDK，不应再机械地要求“把所有 synchronized 都换掉”。涉及 native 或外部函数调用等场景，仍需要结合实际栈和监测结果分析。

这体现了一个通用观点：**经验是带条件的结论。运行时变了，条件也可能变了。**

## 四、语言不同，后端的基本问题不会消失

Java 的优势是成熟的业务开发生态和长期积累的工具链；Go 常适合网络服务、基础设施工具和部署要求简洁的服务；TypeScript / Node.js 对前后端协作、BFF 和大量 I/O 的接口开发很方便；Python 在数据处理和 AI 生态里有明显便利；Rust 适合需要严格控制资源、延迟和内存安全的部分组件。

这些只是常见适配方向，不是性能排名。同一种语言也能实现很多类型的系统。

换语言之前，先回答：现在慢在哪里？是运行时 CPU 不够，还是一条没建索引的 SQL？是语言内存开销大，还是每个请求把整张表读进了内存？是框架太重，还是服务启动时顺便调用了十几个外部系统？

把 Java 换成 Go，不会修复重复扣库存；把 Node.js 换成 Rust，也不会自动让接口具备权限检查。

跨语言都适用的一条原则是：**先识别限制系统的那一种资源，再优化它。**

另外，语言运行时也要按官方维护状态选版本。例如 Node.js 项目应检查[发布与支持时间表](https://nodejs.org/en/about/previous-releases)，不要把某个年代的版本编号规律当成永远成立的规则。

## 五、模块化单体，是很多团队值得认真考虑的起点

微服务解决的是独立部署、独立扩缩容、团队自治和故障隔离等问题。它同时引入网络调用、跨服务一致性、接口版本和运维协作问题。

如果一个人维护订单、商品、支付三个服务，改一次需求要同步发三个版本，这不一定比一个边界清晰的应用更有效。

模块化单体的思路是：先在一个部署单元里把边界划清。

```text
application
├── ordering     订单状态与下单规则
├── inventory    库存预占、释放与确认
├── payment      支付请求、回调与对账
└── notification 通知与发送记录
```

这种结构按业务职责组织代码，而不是把所有模块的 controller、service、mapper 各自堆在一起。订单模块可以请求库存模块提供的能力，但不应随意修改库存模块内部的表和对象。

[Spring Modulith](https://docs.spring.io/spring-modulith/reference/fundamentals.html)提供模块结构校验、模块测试等能力，可以帮助把这种约定变成可检查的规则。即使不用它，依赖检查和清晰的模块接口也能实现相近目标。

但分了目录不等于有了边界。真正的边界还包括：谁能修改这份数据、哪些状态变化必须一起发生、外部模块可以依赖什么、内部实现能否自行调整。

什么时候值得拆服务？比如报表任务持续拖慢交易接口，需要单独扩缩容；支付模块有独立团队和发布节奏；某个模块必须有独立的安全隔离。此时拆分有明确收益。

**把服务拆开很容易，把一次故障的责任和恢复流程说清楚更难。后者应该先发生。**

## 六、关系数据库仍然是很多系统最重要的基础设施

数据库不只是“把对象存起来”。它承担了约束并发、保存事实、建立索引和提供恢复依据的责任。

PostgreSQL 18 的[官方发行说明](https://www.postgresql.org/docs/18/release-18.html)中，有异步 I/O、多列 B-tree 索引的 skip scan、`uuidv7()` 等变化。这些能力值得研究，但不会替代查询计划分析。

例如，skip scan 可以在满足条件时改善多列索引的利用方式，不代表联合索引从此不需要考虑列顺序。`uuidv7()` 提供带时间特征的 UUID，也不表示跨机器生成的业务事件拥有严格全局顺序。

比追逐新特性更优先的，是把业务规则写到适当的位置。

### 不要用“先查再改”假装自己有并发控制

下面这段逻辑看起来没问题：

```text
查询库存是 1
如果库存大于 0
    将库存减 1
```

但两个请求都可能同时查到 1，然后各自认为自己可以购买。

一种常见做法是让扣减条件与更新在一条 SQL 中完成：

```sql
UPDATE inventory
SET available = available - :quantity
WHERE sku_id = :sku_id
  AND available >= :quantity;
```

要求 `quantity` 是经过校验的正数，再检查实际影响的行数：更新到一行，表示成功；零行，表示商品不存在或可用库存不足。

如果库存表和订单表处于同一个事务数据库中，可以把库存预占、订单写入和待发送事件写入放在同一短事务里。只要其中一步失败，就整体回滚。数据库中也可以增加非负约束作为额外防线。

如果库存和订单已经属于不同数据库，这段本地事务方案就不成立，需要明确预占、超时释放和对账等跨边界流程。

### 索引不是越多越保险

对“某个用户最近的订单”这样的查询，一个匹配过滤与排序的复合索引通常比单纯加机器更有针对性。索引会增加写入和存储开销，还需要结合实际分布查看执行计划。

游标分页也值得认真理解。以 `(created_at, id)` 为稳定排序键，比深度 `OFFSET` 更容易避免扫描大量已经跳过的行。但如果排序字段会变化，或用户要求固定快照，仍需要额外设计。

新数据库版本能改善执行方式，好的数据模型则决定数据库到底需要做多少工作。

## 七、幂等：允许请求重来，不允许业务重复发生

用户点击付款后，页面转了十秒，没有结果。他刷新并再次点击。后端收到两次请求并不奇怪。

网络超时只说明调用方没有在期限内拿到结果，不能证明服务端没有成功。因此，“失败就重试”必须和幂等一起设计。

一种常见的接口约定是客户端为一次业务意图生成幂等键：

```http
POST /orders
Idempotency-Key: 6ebf...一次下单动作的唯一标识
```

服务端不应只在内存里记录这个键。多实例和重启都会让记录失效。可以在数据库中保存：所属用户或租户、操作类型、幂等键、请求摘要、执行状态和结果引用，并对作用域内的键加唯一约束。

同一个键携带不同金额或不同商品，应当明确拒绝，而不是返回另一份请求的结果。同一个键再次出现且原请求仍在处理中，也要有确定语义，例如返回处理中状态，并提供查询地址。

如果实际动作涉及外部支付平台，本地幂等表也无法替代对方的幂等能力。需要使用稳定的商户请求号、查询接口、签名验证和对账流程处理“结果未知”。

这背后的通用观点是：**后端需要管理的不只是成功和失败，还有结果尚不确定。**

## 八、缓存保存常用答案，数据库保存业务事实

Caffeine 可以减少同一进程反复读取热点数据的开销，Redis 可以让多个实例共享缓存。组合使用时，还要考虑每层数据的有效期和失效传播。

商品名称暂时旧几秒，通常可以接受；库存扣减和付款金额则不能直接相信一份可能过期的展示缓存。

把不同的数据分清，会比给所有键统一加一个过期时间更可靠：

| 数据 | 可以接受的处理方式 | 必须守住的边界 |
| --- | --- | --- |
| 商品介绍 | 短时间缓存，异步刷新 | 控制失效后的集中回源 |
| 订单列表展示 | 按业务接受短暂延迟 | 支付后要能查询到权威状态 |
| 库存预占 | 事务或有明确恢复机制的库存方案 | 不能靠过期展示值判断能否出售 |
| 权限结果 | 谨慎缓存，支持撤销传播 | 敏感操作需要满足撤权时效要求 |

关于本地与共享缓存的具体读写流程，可以接着看[《Caffeine + Redis：用商品详情页讲清后端多级缓存》](/blog/backend-multi-level-cache/)。

缓存设计最容易被忽略的问题是：缓存全部失效时，系统还能不能工作？如果一失效就把数据库打垮，这层缓存已经从性能优化变成了可用性依赖。要提前考虑请求合并、并发限制、预热或适当降级。

## 九、事件驱动的价值，在于把失败变得可恢复

订单创建后要发通知、更新搜索索引、生成报表。把所有动作都串在下单接口里，会拉长响应时间，也会让一个邮件服务故障拖垮下单。

消息队列能把这些工作分开，但它不能自动解决数据库和消息之间的双写问题。

```text
数据库提交成功 → 进程崩溃 → 消息还没发出去
```

如果换个顺序先发消息，消息消费者又可能在订单提交前收到事件，甚至订单最终回滚。

### Outbox：先在同一个事务里记下“还有一件事要做”

Outbox 的办法是：业务事务提交时，同时向本地事件表写入一行。它不是立刻保证外部系统成功，而是保证这件待办不会凭空消失。

```text
一个数据库事务
├── 写订单
├── 预占库存
└── 写 outbox 事件

提交后
outbox → 可靠转发 → 消息队列 → 消费者
```

转发可以由轮询任务实现，也可以使用 Debezium 等 CDC 工具读取已提交的变更。[Debezium Outbox Event Router](https://debezium.io/documentation/reference/stable/transformations/outbox-event-router.html)说明了事件 ID、聚合 ID 和消息键的用法。

轮询更容易起步，但需要处理任务抢占、发送后确认、重试和清理；CDC 可以减少业务轮询，却增加了连接器、日志保留和运维要求。二者都有成本。

### 消息重复，是需要设计的正常情况

转发器发完消息，还没来得及标记成功就崩溃，恢复后会再次发送。消费者处理完成，还没确认消息也可能崩溃。很多可靠消息链路因此采用至少一次投递。

消费者可以通过唯一事件 ID 去重，但“记下已消费”和“修改本地业务状态”应尽量在同一本地事务中完成。否则先记消费成功再崩溃，业务动作就丢了；反过来则可能重复执行。

如果动作是发短信、调用外部付款接口，本地事务不能包住外部系统，还要使用对方的幂等能力和补偿机制。

Kafka 等系统提供的某些 exactly-once 能力有明确作用域，不能直接推导出“我的数据库、支付和发货都恰好执行一次”。

### 顺序也要先说明范围

同一订单的“已付款”通常应该先于“已发货”被正确处理；全站所有订单排成一个严格队列，往往没有必要。

可以按订单 ID 分区，结合版本号、状态检查和重放策略处理乱序。即使队列保持了某个分区的顺序，消费者并发处理、失败重试和多来源事件也可能影响最终应用顺序。

所以真正的约束是：一个事件到来时，系统能不能判断它是否仍然适用。

## 十、长流程需要持久化状态，不需要长时间占着数据库事务

付款可能等几分钟，人工审核可能等三天。把数据库事务一直开着等待，既占连接，也持有锁，还容易超时。

更合理的做法是把过程表示为明确状态：

```text
待付款 → 已付款 → 待发货 → 已完成
   │         │
   ▼         ▼
 已取消    退款处理中 → 已退款
```

每次状态变化用一个短事务完成。等待外部结果时，保存当前状态和下一步计划，让进程重启后也能继续。

Temporal 等[持久工作流工具](https://docs.temporal.io/temporal)可以通过事件历史等机制帮助恢复长流程。它减少了手写调度和恢复代码的负担，但不会让外部扣款自动具备幂等，也不会把多个数据库变成一个事务。

对于简单流程，一张状态表加可靠的定时扫描可能就够用；步骤多、等待久、恢复逻辑复杂时，再评估工作流平台。

还要区分补偿和回滚。包裹已经发出之后，“取消发货”不是让历史消失，而是启动退货或拦截流程。业务补偿本身也会失败，需要被记录、重试和人工处理。

## 十一、接口的成熟，体现在调用方知道下一步怎么做

接口设计常被简化成 URL 应该用名词还是动词。更实际的问题是：调用失败时，客户端能不能正确处理？

一个库存不足错误应该和服务暂时不可用区分开。前者需要用户调整购买数量，后者才可能适合等待或重试。

可以约定结构化错误：

```json
{
  "code": "INSUFFICIENT_STOCK",
  "message": "库存不足，请调整购买数量",
  "requestId": "req_7b92..."
}
```

对外保持稳定的业务错误码，对内通过 requestId 关联链路与日志。不要直接把数据库错误、堆栈和内部地址返回给用户。

OpenAPI 适合描述 HTTP 契约，并用于生成文档、客户端或兼容检查。gRPC 在内部强类型调用、流式通信等场景有优势，但浏览器接入、调试方式和团队经验也要算进成本。

无论协议如何，都需要讨论字段新增、字段删除、枚举扩展和默认值变化。服务端加了一个新枚举值，旧客户端是否会直接崩溃？这类问题往往比选择 REST 还是 RPC 更影响稳定性。

## 十二、可靠性的关键，是让系统在忙不过来时仍然有秩序

系统不会因为使用了异步框架、虚拟线程或消息队列，就获得无限容量。

当请求到达速度长期大于处理速度，队列必然增长。队列只是把拒绝变成了等待，如果等待没有上限，最终会把内存、连接和用户耐心一起耗尽。

### 给一条调用链分配时间预算

假设订单接口希望在 800 毫秒内给出响应。不能同时让数据库最多等 800 毫秒、支付接口再等 800 毫秒、缓存故障又额外重试一轮。

应当把总期限向下传递，给连接获取、请求执行和必要重试分别留出空间。上游已经取消的工作，如果下游仍然持续执行，也会继续浪费资源。

超时值应来自依赖延迟分布、业务容忍度和故障表现，不宜整站统一写成一个整数。

### 重试有乘法效应

假设 A 调 B，B 调 C，每层最多尝试三次，最坏情况下一个入口请求可能在 C 产生九次调用。再多一层会放大到二十七次。

依赖越忙，调用方越重试，就越容易一起失去响应。常见控制办法包括：有限重试次数、指数退避、随机抖动、整体重试预算，以及只重试确实可安全重试的错误。

限流、并发限制、熔断、降级各有用途：限流控制进入速度，并发限制控制同时占用的资源，熔断避免持续冲击已知故障的依赖，降级则明确说明哪些能力可以暂时简化。

这些机制不能代替业务判断。商品推荐可以暂时省略，支付金额不能降级成一个猜测值。

## 十三、可观测性：从“机器没死”走到“用户完成了什么”

CPU 只有 20%，用户依然可能无法下单：请求都在等数据库锁，或者支付回调已经堵了半小时。

因此，要从用户结果定义指标，例如下单成功率、支付确认延迟、超时未释放库存数量、消息最老积压时间。

[OpenTelemetry](https://opentelemetry.io/docs/concepts/signals/)提供了遥测信号与相关标准、采集能力。它不等于存储和查询平台；通常还要配合指标、日志和链路的后端系统。

三类信息各自回答不同问题：

| 信息 | 擅长回答 |
| --- | --- |
| 指标 | 从什么时候开始，大约有多少请求受到影响？ |
| 链路 | 这一次请求慢在数据库、缓存还是外部接口？ |
| 日志 | 某个状态为什么被拒绝，当时发生了什么？ |

它们需要用上下文关联。HTTP 到消息队列之间也要考虑传播链路上下文，同时避免把敏感业务数据不加判断地放进上下文。

平均响应时间可能掩盖长尾。p95、p99 能帮助看见少量很慢的请求，但要理解统计窗口、样本量和直方图配置；多个实例的百分位数也不能简单取平均。

另一个常见坑是把订单 ID、用户 ID 都放进指标标签。取值数量巨大，会导致时间序列爆炸。这些高基数字段通常更适合受控的日志或链路属性，并做好脱敏和访问控制。

告警应尽量对应用户影响，且有人知道怎么处理。一个每晚叫醒人、却永远没人行动的告警，只会消耗注意力。

## 十四、部署不是上传文件，而是一次可控的状态变化

容器统一了应用运行的部分环境，但数据库、配置、密钥和网络策略不会自动变得一致。

对于小团队，托管应用平台或简单的容器部署，可能比自己维护 Kubernetes 更合适。Kubernetes 擅长调度和控制资源状态，同时也需要集群升级、网络、存储、安全和故障排查能力。

需要认真建立的是交付路径：代码审查、自动测试、构建产物、配置分离、小范围放量、指标观察和回退。

数据库变更尤其需要兼容新旧版本并存。一个常用过程是：

1. 先增加新字段或新表，保持旧应用仍能工作。
2. 部署兼容代码，必要时迁移历史数据并核对结果。
3. 将读写切换到新结构，观察一段时间。
4. 确认旧代码已经退出，再删除旧结构。

这通常被称为 expand-contract。并不是所有变更都能无锁完成，大表 DDL、索引构建和数据回填需要结合数据库能力安排。

回滚应用镜像不等于回滚数据。如果新版本已经错误退款，仅仅切回旧代码不会把钱自动追回。

更完整的云部署与恢复思路，会在[《云计算到底替我们做了什么》](/blog/cloud-computing-architecture-and-tradeoffs/)中展开。

## 十五、安全需要落在每一次数据访问里

登录成功只说明身份已验证，不说明这个用户可以访问任意订单。

接口收到 `GET /orders/123` 时，要检查当前身份是否有权读取订单 123。多租户系统还要确保查询、缓存键、消息和后台任务中的租户边界一致。

[OWASP 的对象级授权风险说明](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)把这种问题列为重要 API 风险。不能因为页面上没有显示其他人的订单入口，就认为接口已经安全。

服务端应从可信身份上下文获取用户和租户，而不是直接相信请求体传来的 `userId`。数据库查询、业务授权和必要的行级策略可以共同防护，但任何一层都需要测试。

此外，参数化 SQL、密钥管理、依赖漏洞更新、最小权限和审计记录都是长期工作。支付密钥不能跟着镜像公开，日志不能顺手打印完整令牌。

一个值得保留的通用观点是：**权限是业务规则的一部分，应该和状态变化一起被设计。**

## 十六、AI 进入后端之后，传统工程问题会更明显

现在的后端越来越可能调用模型，做检索问答、内容处理和流程辅助。模型接口只是新增的一种依赖，它同样有延迟、配额、费用和故障。

而且它还有一类传统接口较少出现的特征：输出可能语法正确、意思却不对。

因此，接入 AI 时需要同时考虑两种质量：服务能不能稳定返回，以及返回结果能不能完成任务。前者用超时、限流、观测处理，后者需要样本集、评测、来源核对和人工反馈。

数据量和检索要求允许时，PostgreSQL 搭配 [pgvector](https://github.com/pgvector/pgvector)可以作为初期方案，减少一套独立存储。但近似检索、租户过滤和权限条件会影响召回，不能因为 SQL 中加了 WHERE 就认为召回质量和授权流程都已解决。

Agent 调工具时，工具调用应被当成不可信请求处理：校验结构、校验权限、限制金额或次数、记录审计，涉及高影响操作时安排适当确认。模型不能因为生成了一段 JSON，就自动获得转账或删除数据的权限。

RAG 的细节可以看[《RAG 的几种常见用法，以及怎样把它做稳》](/blog/rag-in-practice/)。后端的价值仍然在于把不确定能力放进有边界、能恢复、能追踪的流程。

## 十七、测试要验证系统的承诺，而不只是验证函数被调用

如果一次重构改变了类名和调用方式，业务行为没有变，测试就不应大面积失效。相反，如果接口仍然返回 200，但库存少扣了一次，测试应当发现。

对订单系统，值得覆盖的是这些情形：

- 两个请求争抢最后一份库存，只有一个成功。
- 同一幂等键重复提交，只有一张订单；换了请求内容会被拒绝。
- 事务提交后进程退出，待发送事件仍能被找回。
- 同一事件消费两遍，业务效果没有重复。
- 无权访问订单的用户，即使知道 ID 也无法读取。
- 新旧应用版本并存时，都能使用迁移中的数据结构。

纯计算规则适合单元测试，数据库约束、隔离和 SQL 行为则需要集成测试。Testcontainers 这类工具可以帮助在测试中使用真实数据库或消息系统，但容器测试也不会自动覆盖生产环境的网络、规模和权限配置。

压测除了看最高吞吐量，还应该观察超过容量后系统怎样退化，以及压力撤走后是否能恢复。故障注入则应控制范围，先验证超时、重复和短暂不可用等具体假设。

## 十八、三种规模，三种合理的起步方式

下面是按团队阶段给出的建议，不是行业统一答案。

| 场景 | 起步组合 | 优先补齐 |
| --- | --- | --- |
| 个人项目或小型产品 | 熟悉的语言框架 + 模块化单体 + 关系数据库 + 对象存储 + 自动部署 | 业务约束、备份恢复、错误追踪、最基本的权限 |
| 小团队业务系统 | 上述基础 + 按需缓存 + 可靠后台任务或消息队列 + OpenTelemetry | 幂等、Outbox、容量预算、灰度和数据库迁移 |
| 多团队或明显规模压力 | 按职责拆分服务 + 合适的托管基础设施 + 平台标准 | 接口兼容、跨域流程、租户隔离、故障演练和成本归属 |

关键不是让所有项目最终长成第三行，而是让每次增加复杂度都有明确收益。一个长期稳定、成本可控的单体，不需要为了证明先进而拆成二十个服务。

## 十九、把一次下单重新走一遍

现在再看订单创建，完整过程可以是这样：

```text
请求进入
  → 验证身份、权限、参数和请求期限
  → 检查幂等键及请求摘要
  → 在容量允许的范围内进入业务处理
  → 本地事务：预占库存、创建订单、写入 Outbox
  → 返回订单标识和确定的当前状态

事务之外
  → 转发已提交事件
  → 消费者幂等处理通知、索引等工作
  → 支付结果经过签名验证与状态校验后推进订单
  → 超时扫描、查询与对账处理遗漏和结果未知

整个过程
  → 指标看用户结果，链路看耗时，日志解释状态变化
```

如果系统规模还小，其中一些步骤可以由同一个进程完成。随着规模增长，也可以把它们拆到不同服务。部署形态变了，正确性边界仍然要存在。

## 二十、几条值得长期保留的后端观点

**业务事实要有明确归属。** 谁负责最终库存、最终支付状态、最终权限，要能说清楚。多份副本可以帮助读取，但不能让责任一起分散。

**重要规则要能被系统执行。** 文档上写“不会重复下单”，不如唯一约束、事务、状态检查和幂等处理共同保证。文档负责解释，代码和存储负责执行。

**把结果未知当作一种正式状态。** 网络中断之后，盲目判定失败会制造重复操作，盲目判定成功会制造错误承诺。查询、重试和对账是状态恢复的一部分。

**资源总是有限，排队也有成本。** 异步、虚拟线程和弹性扩容都不能消除瓶颈。系统必须知道何时等待、何时拒绝，以及如何恢复。

**为修复留下路径。** 需要稳定业务标识、状态变化记录、可重放事件和受控的人工操作入口。出了问题只能直接改数据库的系统，通常缺少恢复设计。

**复杂度是一笔持续支出。** 每增加一个服务、队列或数据副本，都要有人负责升级、告警、排障和恢复。只计算接入成本，会高估架构收益。

**可演进比一次设计得很大更有价值。** 清楚的模块边界、可兼容的接口、可迁移的数据和可重复的交付流程，往往比提前使用所有热门组件更能支撑未来。

后端技术更新得很快，但工作始终具体：让数据有依据，让并发有约束，让失败有去处，让下一位维护者能够理解发生了什么。

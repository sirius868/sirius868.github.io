让模型回答一个问题，通常只需要一次输入和输出。让它完成一项任务，情况就不同了：它可能要查资料、读取文件、调用接口，看到结果后再决定下一步。这种**根据观察继续行动**的能力，是理解 AI Agent 的起点。

一个实用的定义是：**Agent 是由模型参与决策、由程序控制执行的任务循环。** 模型负责提出下一步，程序负责验证、执行和记录。把两者分开，才能清楚地回答“它做了什么”“为什么停下”和“出了错怎么办”。

## 从任务循环开始

假设用户问：“找出项目里负责生成 RSS 的代码，并解释文章链接从哪里来。”一个 Agent 可以按下面的顺序工作：

1. 模型选择搜索文件的工具，并给出搜索词。
2. 程序检查工具名和参数，执行搜索，将结果作为观察返回。
3. 模型根据文件路径读取相关代码；程序再次验证并执行。
4. 模型基于读到的内容生成回答，同时指出对应文件。

这里真正重要的不是“思考”文字，而是每一步都有可检查的输入和输出。可以把循环写成一个简化的状态机：

```text
接收任务 → 选择下一步 → 验证动作 → 执行工具 → 记录观察
              ↑                            │
              └────────── 继续 ────────────┘
              └────────── 完成或停止
```

模型可以建议动作，但**是否允许执行**由程序决定。搜索文件和删除文件都可能被模型描述成“下一步”，它们不应拥有相同的权限。

## 把模型输出变成受约束的动作

下面是一个 TypeScript 示意。它只开放 `searchDocs` 一个只读工具，并限制最多执行五步。`model.next` 返回的结构化结果，在进入这个循环前仍需要做运行时校验；类型声明本身不能验证模型输出。

```ts
type Decision =
  | { type: 'tool'; name: 'searchDocs'; input: { query: string } }
  | { type: 'final'; answer: string };

type Message = { role: 'user' | 'assistant' | 'tool'; content: string };

async function runAgent(
  question: string,
  model: { next(messages: Message[]): Promise<Decision> },
  searchDocs: (query: string) => Promise<string>
): Promise<string> {
  const messages: Message[] = [{ role: 'user', content: question }];

  for (let step = 0; step < 5; step++) {
    const decision = await model.next(messages);
    if (decision.type === 'final') return decision.answer;

    // 实际服务还应验证 query 的长度，并为工具设置超时。
    const observation = await searchDocs(decision.input.query);
    messages.push({ role: 'assistant', content: JSON.stringify(decision) });
    messages.push({ role: 'tool', content: observation });
  }

  throw new Error('Agent 超过步骤上限，任务未完成');
}
```

这个例子省略了具体模型 SDK，但保留了关键边界：工具列表由程序定义，模型不能随意发明一个可执行命令；循环有明确上限；工具结果会进入下一轮上下文。生产环境还要校验结构化输出、限制参数和结果大小，并处理超时与工具异常。

## 状态、记忆和上下文不是一回事

Agent 要“记住”的内容至少有三类：

- **当前任务状态**：目标、已执行的动作、观察结果和剩余预算。它决定这一轮任务如何继续。
- **外部事实**：文档、数据库记录或网页内容。它们需要来源、时间和访问权限，不能仅凭模型复述就当作事实。
- **长期偏好**：用户明确保存的设置，例如回答语言或输出格式。它们不应从一次对话中被擅自永久推断。

把全部历史塞进提示词，既昂贵，也容易让旧信息干扰当前任务。更稳妥的办法是保存结构化执行记录，并在每一步只提供完成下一步所需的上下文。检索到的文档是**不可信输入**：其中即使写着“忽略之前的指令”，也只能作为待分析的文本，不能提升为系统规则。

## 可靠性从边界开始

一个能演示成功的 Agent，距离能长期运行的 Agent 还有几道边界：

1. **步骤与成本预算**：限制模型调用次数、工具调用次数、运行时间和结果大小。达到上限时，返回已完成的部分与未完成的原因。
2. **工具权限**：按任务开放最少的工具。写文件、发消息、付款或部署等动作，应有明确的授权范围和必要的确认点。
3. **失败处理**：区分“没有找到结果”和“工具执行失败”。重试要有次数上限；对会产生副作用的操作，还要考虑重复调用是否会造成重复提交。
4. **可追踪记录**：记录动作、参数摘要、耗时、结果状态和错误，避免在日志中保存密钥或不必要的个人数据。
5. **完成条件**：让程序能判断任务是否真的结束。例如“已生成文件且通过构建”比“模型说已经完成”更可验证。

所谓自主性，不是去掉这些边界，而是在边界内让系统自行选择下一步。

## 用任务评测，而不是只看单次回答

评测 Agent 时，应准备一组有明确目标和初始状态的任务。例如“找出 RSS 链接生成位置”，不仅检查最终解释是否正确，还检查它是否读取了正确文件、有没有调用无关工具、是否在预算内完成。对于可能修改外部状态的任务，最好在隔离环境中运行，并检查最终文件或数据库状态。

一次成功的演示只能说明那次路径可行。把成功率、平均步骤数、耗时、成本、错误类型和需要人工接管的比例一起记录，才能看出系统改动究竟带来了什么。

## 一个可落地的起点

第一次实现 Agent，不必先做复杂的多 Agent 协作。选择一个范围清楚的任务，提供一两个只读工具，定义结构化动作、步骤上限和完成条件，再用真实任务样本反复测试。当单个执行循环能够稳定地给出可追溯结果，再增加写入能力或更长的任务链。

Agent 的价值不在于它“像人一样工作”，而在于它能把模型的判断接到真实工具上，同时让每次行动都有边界、有记录、可验证。

第一次接触云计算，很容易把它理解成“租一台远程电脑”。购买云服务器，装 Java，启动应用，绑定域名，网站就能访问了。

这个理解没有错，但只解释了很小一部分。

等到用户变多、数据库故障、账单上涨，或者有人问“某个机房断电之后还能不能下单”，问题就会变成：云平台究竟替我们承担了哪些工作？剩下哪些工作，仍然只能由我们自己完成？

云计算真正改变的是资源的获取方式、系统的责任边界，以及为可靠性付费的方式。它让基础设施可以通过 API 创建和调整，也让很多过去需要自己维护的能力变成可购买的服务。

代价是：你需要理解这些服务的边界。买了高可用数据库，不代表业务一定高可用；把应用放进 Kubernetes，不代表数据自然安全；用了按需计费，也不代表账单一定更低。

这篇文章继续使用一套订单系统作为例子，逐层看云上系统如何工作，以及每一层该怎样判断。文中的容量、费用和恢复目标都只是示意，不代表任何云厂商的实际报价或承诺。具体功能、区域支持和服务条款以部署时的官方文档为准，资料核对于 **2026 年 10 月 31 日**。

## 一、先看一笔订单经过了哪些云资源

一个常见的云上系统，可以画成这样：

```text
用户
 │
 ▼
DNS → CDN / 边缘防护
             │
             ▼
         负载均衡
          │     │
          ▼     ▼
        应用 A 应用 B
          │     │
          ├─────┼──→ 数据库
          ├─────┼──→ 缓存
          ├─────┼──→ 消息队列 → 后台任务
          └─────┴──→ 对象存储

贯穿各层：身份权限、密钥、日志、指标、备份与费用
```

DNS 负责把域名指向入口。CDN 可以在边缘缓存适合公开分发的资源，减轻源站压力。负载均衡把请求分给应用实例。应用读取数据库中的业务事实，把文件交给对象存储，把不必同步完成的工作交给后台处理。

这些组件并不要求每个项目都配齐。一个静态博客可能只需要构建平台和静态托管；一个低流量接口也可能用一台应用实例加托管数据库起步。

这张图的价值在于帮助检查依赖：如果每个请求最终都依赖同一台数据库，那么前面加十个应用实例，也不能绕过数据库的容量和故障边界。

## 二、云的本质：资源可以编程，责任可以重新分配

自己买服务器时，需要采购、上架、布线、安装系统，再规划容量。云平台把其中很多工作封装成了 API。

你可以通过配置创建网络、服务器和数据库，也可以在业务低谷时减少部分计算资源。基础设施因此能够跟着代码一起审查、复制和变更。

但不同服务替你承担的范围不同。

| 形态 | 常见例子 | 平台主要承担什么 | 使用方仍需承担什么 |
| --- | --- | --- | --- |
| IaaS | 云主机、虚拟网络、云硬盘 | 物理设施和底层虚拟化等 | 操作系统、应用、补丁、数据与网络配置 |
| 托管运行平台 | 托管容器、应用平台 | 更多运行环境和调度工作 | 应用逻辑、依赖、权限、容量和配置 |
| 托管数据库 | 托管关系数据库 | 按服务范围处理实例维护、备份或故障切换 | 表结构、查询、账号权限、恢复策略和业务一致性 |
| Serverless | 函数、按请求运行的计算服务 | 更多实例生命周期管理 | 事件语义、并发、超时、数据和费用控制 |
| SaaS | 成品邮件、协作或业务服务 | 完整产品的运维 | 租户设置、访问管理、数据使用和集成 |

这些分类有重叠，不能只看产品营销名称判断责任。[AWS 共享责任模型](https://aws.amazon.com/compliance/shared-responsibility-model/)就强调，责任会随所用服务而变化。

一个直接的例子是数据库：平台可以帮你更换故障硬件，但不会替你阻止一条有权限执行的错误删除语句。平台可以提供备份能力，但保留多久、能否恢复到需要的时间、恢复之后如何验证，仍然需要你安排。

**购买托管服务，是把部分工作交给平台，并不是把业务责任交出去。**

## 三、计算：云主机、容器和函数，选择的是不同的控制程度

### 云主机：控制直接，维护工作也直接

云主机适合需要自定义操作系统、运行环境或特殊软件的场景。它通常更容易对应传统服务器的思路，也方便排查一些底层问题。

但你仍需要处理系统补丁、进程托管、日志轮转、容量和部署。把 jar 文件放到服务器上执行，只解决了“现在能启动”，没有解决重启、更新和故障恢复。

### 容器：统一应用交付，不会抹平基础设施差异

容器把应用和一部分运行环境打包起来，让同一个产物更容易在测试与生产中运行。

它没有把数据库、网络策略、CPU 架构和存储性能一起打包。一个容器在本地正常，在云上仍可能因为内存上限、只读文件系统、时区配置或权限而失败。

容器镜像也不是“越小越安全”的简单竞赛。需要关注依赖来源、构建可追踪性、漏洞修复和运行权限。使用非 root 用户、减少不需要的能力、固定并更新基础镜像，往往更具体有效。

### Serverless：平台管理实例，你管理调用行为

Serverless 经常被解释为“没有服务器”。更准确的说法是：使用方不直接管理大部分服务器生命周期。

它适合流量有明显波动、事件驱动、任务可拆分的场景，比如图片处理、Webhook 接收和定时任务。长时间稳定高负载的工作，也可能由普通容器或主机运行得更经济，需要实际计算。

使用函数平台前要确认：最大执行时间是多少？冷启动表现如何？并发到来时会创建多少实例？连接数据库会不会把连接数耗尽？失败事件是重试、丢弃，还是进入失败队列？

尤其不能统一假定所有触发方式都是恰好一次。HTTP 调用、消息触发和对象事件的重试、顺序语义可能不同，业务动作仍需要幂等。

选择这三类计算形态，可以围绕一个问题展开：**你希望保留哪些控制权，又愿意为哪些运维工作付费？**

## 四、存储：同样叫“存数据”，访问方式却完全不同

应用里的“存储”至少包含四类需求。

| 类型 | 适合保存什么 | 访问方式和关键特点 |
| --- | --- | --- |
| 块存储 | 数据库数据盘等 | 像磁盘一样读写块，关注 IOPS、吞吐、延迟和挂载限制 |
| 文件存储 | 共享目录、需要文件系统语义的应用 | 以路径访问文件，关注权限、并发、锁与元数据性能 |
| 对象存储 | 图片、附件、备份、数据集 | 通过对象键和 API 访问，关注请求、容量、生命周期和访问策略 |
| 数据库 | 订单、支付记录、用户关系 | 提供查询、索引、事务和约束，关注业务一致性与恢复 |

把对象存储挂载成一个目录，并不保证它就具有本地文件系统的全部语义。把 JSON 文件放进存储桶，也不意味着获得了关系数据库的事务能力。

### 对象存储不是一律“最终一致”

一些旧文章会笼统地说对象存储只能最终一致。这个结论需要按厂商、操作和功能重新核对。

例如，[Amazon S3 用户指南](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html)说明了其对象 PUT、DELETE 等操作后的强读后写一致性。这不代表多个对象的写入自动构成事务，也不代表跨区域复制或所有兼容 S3 API 的产品都有相同保证。

如果一份报告由“文件对象”和“数据库记录”共同组成，应明确发布流程。例如先上传对象，再验证结果，最后将记录置为可见；中间失败留下的孤立对象，需要清理任务处理。

### 本地磁盘不应该悄悄成为唯一副本

应用把用户上传的附件放在某个容器目录里，换实例后文件不见了，这是常见事故。

临时磁盘可以放可重建缓存和中间结果。必须长期保存的对象，应放入有明确持久性、备份和权限方案的存储。即使挂载了持久卷，也要理解它的故障域和恢复方式。

文件名也不是权限。知道一个难猜的链接，不应该成为私有合同或证件的唯一保护。可以通过鉴权后签发短期访问地址，并注意链接过期前仍可能被转发使用。

## 五、网络：画了一个私有子网，不等于系统自动安全

云网络最容易让人被缩写淹没。先按功能理解会更清楚。

VPC 或类似虚拟网络提供逻辑隔离的网络空间；子网组织地址与部署位置；路由决定数据往哪里走；安全组或防火墙规则控制允许的连接。

“公有子网”和“私有子网”的具体定义依平台而异，一般需要结合通往互联网的路由和资源地址判断。没有公网 IP，不代表资源完全没有出站网络；有些流量会经过 NAT 或私有端点。

NAT 常用于让内部资源主动访问外部网络，而不让互联网直接发起相同方式的入站连接。它不是用户身份认证，也不能替代应用权限。私有端点通常可以让访问某些云服务的流量走平台提供的私有路径，但有服务覆盖、DNS 配置和费用等条件。

### 网络连通、传输加密、身份授权，是三件事

数据库端口只允许应用访问，是网络限制；连接使用 TLS，是传输保护；应用账号只能访问所需表，是权限限制。

这三层互相补充。一个位于内网、拥有数据库全权限的应用，仍可能因为 SQL 注入造成严重损失。

内部通信也不应因为“都在同一个 VPC”就完全信任。服务身份、短期凭证、最小权限和必要的 TLS，能让被攻破的单个组件更难横向扩散。

### 网络拓扑也会出现在账单和延迟里

跨可用区、跨区域、NAT 转发和公网出站可能有不同费用，具体取决于服务和定价。把高频交互的应用和数据库随意放在遥远区域，还会把每次网络往返变长。

优化时要先画真实数据流：谁调用谁、每秒多少次、每次多少数据、经过哪些中间设备。很多成本与性能问题，在这张图上比在代码里更容易看懂。

## 六、地域和可用区：高可用首先是故障边界问题

地域通常对应一个地理范围，可用区是地域内具有一定基础设施隔离的部署单元。不同平台的定义和具体实现应查文档。

[Azure 的可用区说明](https://learn.microsoft.com/en-us/azure/reliability/availability-zones-overview)指出，可用区具有独立电力、冷却和网络基础设施，并区分单区和跨区冗余资源。有些服务需要主动配置，才会跨区部署。

这带来一个很实用的检查方式：

- 两个应用进程在同一台主机上，只能防止部分进程级故障。
- 两台主机在同一个可用区，可以分散主机故障，但仍有区级共同风险。
- 应用分布到不同可用区，还要检查数据库、负载均衡和关键依赖是否也具备相应能力。
- 跨区域部署可以应对更大范围故障，却增加数据同步、路由和运维复杂度。

备了两个实例，如果它们都依赖一个无法恢复的数据库，整体仍然存在关键单点。反过来，某个依赖只有单实例，但业务允许临时排队且能可靠恢复，也不一定必须立即升级为多活。

高可用设计应沿着用户完成一次操作的路径逐个检查，而不是只数服务器数量。

## 七、为什么云服务的 SLA 不等于你的用户体验

平台给某项服务提供 SLA，通常有明确的适用配置、统计口径、排除条件和赔付方式。它不是对你整套业务每一次请求的保证。

假设一个简化链路依次需要三个服务都可用，每个可用率都是 99.9%。如果把它们近似看成独立故障，串联系统可用率约为：

```text
0.999 × 0.999 × 0.999 ≈ 99.70%
```

这只是帮助理解依赖影响的数学示例。真实故障往往相关，服务也可能有重试、缓存和降级，不能直接用这个乘法当正式 SLA 计算。

同时，一个组件“健康”并不代表订单能成功。数据库连接池耗尽、第三方支付变慢、权限配置错误，都会让业务失败。

因此需要建立自己的 SLI 和 SLO：SLI 是观察到的服务表现，SLO 是希望达到的目标。比如“有效下单请求的成功比例”，就比“主机存活比例”更接近用户体验。

[Google SRE 关于 SLO 的章节](https://sre.google/workbook/implementing-slos/)强调用可靠性目标指导决策。目标越高，成本和交付约束通常也越高。不能只写一个 99.99%，却没有说明统计窗口、有效请求定义、维护期和依赖范围。

错误预算则把允许的失败变成可讨论的数量：当稳定性持续偏离目标时，是继续加速发布，还是先修复风险，应有共同依据。

## 八、备份、复制和容灾，解决的是不同问题

这三个概念经常被混用。

**复制**把数据变化传到其他副本，帮助提高可用性或读取能力。但一条误删除也可能被很快复制过去。

**备份**保留某个历史状态，帮助在误操作、损坏或其他事故后恢复。它不保证恢复足够快，也不保证保留了刚写入的数据。

**容灾**是让整套业务在较大范围故障后恢复工作，包含数据、应用、配置、网络、身份、依赖和操作流程。

只备份数据库，但密钥、对象文件或部署配置都找不到，业务仍然恢复不了。

### 用 RPO 和 RTO 把要求说具体

RPO 是可接受丢失多久的数据；RTO 是可接受业务中断多久。

假设业务要求 RPO 不超过五分钟、RTO 不超过三十分钟，就需要验证：实际恢复点距离故障有多远，从宣布恢复到用户重新完成下单又用了多久。

“每天凌晨备份一次”不能自然满足五分钟 RPO；“文件已经备份”也不能证明三十分钟内能恢复一个大数据库。

### 恢复能力必须演练出来

一次有意义的演练应该实际做这些事：

1. 在隔离环境中恢复数据库和必要文件。
2. 配置应用访问恢复后的资源，验证身份和密钥可用。
3. 检查订单总量、金额、状态及关键业务关系。
4. 验证后台任务不会重复付款、重复通知或误处理真实订单。
5. 记录耗时、人工步骤、缺失信息，再修正流程。

备份也要考虑被攻击者删除的风险。独立权限、保留策略、不可变或跨账户副本等能力可以作为防线，但需要确认服务支持和管理成本。

### 跨区域多活不是容灾的默认终点

多个区域同时写同一份库存，会遇到冲突、复制延迟和网络分区。如何避免超卖、谁有权继续接单、失败后怎样合并数据，都必须有明确规则。

异步复制通常存在数据落后的窗口。同步跨远距离复制又会增加写入延迟，并影响分区时的可用性。所谓“多活零损失”，必须追问具体服务、同步范围和故障假设。

对于许多团队，一个经过演练的备份恢复或热备方案，比没有完整数据语义的双区域写入更可信。

## 九、弹性伸缩：能增加机器，不代表业务立刻能承受更多请求

弹性伸缩往往依据 CPU、并发数或队列长度增加实例。它有用，但存在反应时间。

实例启动、镜像拉取、应用预热、注册健康检查，都需要时间。突发流量在几秒内上来，扩容可能来不及，因此还要有准入控制、排队上限或预先扩容。

更重要的是扩容方向：

```text
应用实例增加 5 倍
    ↓
数据库连接也增加 5 倍
    ↓
数据库先达到上限
    ↓
更多实例一起等待，响应反而更差
```

这种情况下，继续扩应用不能解决问题。需要限制总连接数、减少查询工作、处理热点，或改善数据访问方式。

队列消费者也类似。应观察最老消息年龄和处理耗时，不能只看消息数量；一万条轻任务和一万条十分钟任务，意义完全不同。

缩容同样需要设计：实例是否停止接新请求？长任务怎样交接？未确认消息会不会重投？正在处理的支付回调能否安全重来？

弹性是资源调节能力，业务可恢复性则依赖状态、幂等和退出流程。这些问题在[后端工程篇](/blog/modern-backend-stack-and-engineering/)中有更详细的例子。

## 十、Kubernetes 为什么有用，又为什么不该变成必选项

Kubernetes 可以让你声明希望运行多少实例，控制器持续尝试让实际状态接近期望状态。它也提供服务发现、滚动更新、资源限制和相关扩展机制。

这适合工作负载多、部署需求复杂，且团队能够维护平台的场景。它的价值会随着标准化复用而增长。

但它不会替数据库理解事务，也不会因为声明了三个副本，就让应用自动拥有跨区容灾能力。Pod 分布、存储卷、网络和控制平面都要单独设计。

### 三种探针，不能随便复制粘贴

启动探针帮助判断应用是否完成启动；就绪探针决定实例能否接流量；存活探针用于判断实例是否需要被重启。

如果把数据库短暂不可用直接作为存活探针失败条件，可能导致所有应用一起重启。重启后的初始化再冲击数据库，恢复反而更慢。

探针应当反映对应目的，还要考虑应用实际能否处理部分请求。不是把一个 `/health` 同时填进三个位置就完成了设计。

### 有状态应用需要额外的系统能力

[StatefulSet 官方文档](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/)描述的是稳定身份、存储关联和有序管理等能力。数据库复制、主从选举、备份恢复和一致性，不会因为使用 StatefulSet 自动出现。

托管数据库也因此有价值：你购买的是一部分专业运维能力。当然仍要确认它提供了什么，以及发生超出承诺的故障时怎么办。

### 平台工程是把正确做法变得容易重复

当多个团队都要做日志、密钥、部署、告警和回滚，可以建立统一模板与自助流程。好的平台让开发者用少量配置获得经过验证的能力，并保留必要的排查入口。

如果只是给大家增加一堆必须填写却没人理解的 YAML，平台并没有减少复杂度，只是移动了复杂度。

## 十一、基础设施即代码：能重复创建，也要能安全变更

手工在控制台点出来的配置很难完整复现。基础设施即代码让网络、权限和资源定义进入版本管理，变更可以审查，也更容易重建环境。

Terraform、OpenTofu、Pulumi 以及云厂商自己的模板工具，都可以承担相关工作。选择要考虑团队熟悉程度、服务覆盖和状态管理方式。

但“写进代码”不表示变更就安全。删除一个数据库资源、替换一个网络、修改加密密钥，都可能影响持久数据和访问能力。

需要认真处理：

- 先查看计划，确认修改和替换范围；生产变更要有人理解其影响。
- 状态文件应受访问控制、加密和锁保护，避免并发修改与敏感信息泄露。
- 关键持久资源设置合适的删除保护与保留规则。
- 控制台紧急修改后，要记录并消除配置漂移。
- 区分能自动重建的资源和必须保留历史的数据。

Git 中有一份配置，只证明意图可追踪；恢复时是否拥有权限、容量、配额和数据，还需要另外验证。

## 十二、云上身份：优先让工作负载获得短期权限

如果把一个长期有效、权限很大的访问密钥写进环境变量，然后在所有服务之间复制，泄露一次就可能影响整个账户。

更好的方向是使用平台支持的角色、工作负载身份或联合身份，让服务获得短期凭证。权限按具体资源和操作划分：上传图片的服务，不需要删除数据库备份的权限。

人类管理员、自动部署系统和业务应用，也应该有不同身份。否则审计时只看到同一个账号，难以判断是谁做了什么。

身份之外，还需要秘密管理和加密。KMS 或相关密钥服务可以帮助管理加密密钥，但不会阻止一个本来就有解密权限的应用读取数据。密钥轮换还要兼顾旧数据、旧版本和故障恢复。

另外，开发、测试和生产最好有明确隔离边界，避免测试脚本拿着生产凭证运行。权限配置错误和误操作往往比想象中的复杂攻击更常见，也更值得提前防范。

## 十三、可观测性：先看用户路径，再看资源图表

云平台提供很多图表，但图表数量和排障能力不是一回事。

用户说“付款了却没看到订单”，你需要从业务标识追踪：付款请求有没有发出去，支付平台有没有确认，回调是否通过签名验证，订单状态是否正确更新，展示缓存是否过期。

这需要应用与基础设施的信息能够关联：请求或事件的链路 ID、经过脱敏的业务标识、状态变更记录，以及相关资源的指标。

日志也有成本。每个请求都打印整个请求体，不仅可能泄露敏感信息，还会显著增加采集、索引和保留费用。

要区分审计与调试需求。关键审计记录通常需要完整、受控和有合适保留期；高频调试日志则可以按级别、采样和环境控制。链路采样也要了解可能遗漏哪些低频错误，不能把采样后的请求数直接当完整业务总量。

一套实用告警至少应覆盖用户成功率、关键延迟、积压年龄、容量接近上限，以及备份或恢复链路失效。每个告警都应能对应负责人和处理步骤。

## 十四、云成本：真正需要控制的是单位业务成本

“按需付费”意味着用量与费用更直接地相关，不意味着用量不会失控。

一张账单通常不只有 CPU 和内存：

```text
总费用
  = 计算
  + 存储容量与性能
  + 数据传输
  + 请求与 API 调用
  + 日志、指标和链路
  + 备份与数据保留
  + 托管服务等其他费用
```

有时主机很便宜，NAT 和出站流量更贵；有时对象存储容量不大，海量小对象请求才是主要支出；有时日志平台保存了大量无用内容，比应用本身还贵。

因此，成本优化应该从流量与数据生命周期分析，而不是只找最便宜的服务器。

### 用单位业务成本判断是否健康

假设一个月云资源花费 3,000 元，完成 100 万笔有效业务操作，粗略单位成本是每次 0.003 元。下个月花费涨到 4,000 元，但完成 200 万次，单位成本反而下降。

这个例子只是说明计算方法。实际要明确分母是什么，是否包含开发环境、客服系统和第三方费用，还要结合成功率和用户价值。

[FinOps Framework](https://www.finops.org/framework/)强调让工程、财务和业务共同根据数据管理技术价值。它不只是月底压缩账单，而是让成本有归属、变化有解释、决策有依据。

可以从最基本的动作开始：按项目、环境和负责人标记资源；设置预算与异常提醒；清理闲置资源；调整日志保留；把可中断任务安排到合适的运行方式。

预算告警不一定是自动停机开关，平台费用数据也可能延迟。必须明确真正的配额、并发上限和应急操作。

### 预付折扣和抢占资源，都有适用条件

长期承诺可以换折扣，但会降低调整空间，适合有稳定用量的部分。可被中断的资源适合可重试、可检查点恢复的任务，不适合没有恢复方案的唯一关键实例。

减少一千元资源费，却每周多花两天排障，也许不是划算的优化。总成本还包括人员时间、故障损失和机会成本。

## 十五、托管服务和厂商绑定，要具体到退出路径

使用托管数据库、消息服务和身份服务，可以省掉大量维护工作，也可能让迁移更困难。

但厂商绑定不是只有“完全避免”和“完全接受”两个选择。应当按变化成本分别评估。

业务规则通常值得保持独立；对象上传、支付、消息发布等外部能力，可以通过明确接口封装。对于明显提升生产力的平台能力，也可以在知道退出成本后使用。

真正需要提前回答的是：数据能否完整导出？导出需要多久？导出与迁移期间如何处理新增写入？目标系统有没有等价语义？迁移是否会产生大量传输费用？

只在代码里加一个接口，并不能消除数据格式、事务语义和运维流程的迁移成本。

多云同样如此。把同一个应用放到两家云上，仍可能共用同一套身份、DNS 或数据库。它可能增加成本，却没有达到预期隔离。

先定义要防范的风险，再选择跨账户、跨可用区、跨区域或跨厂商措施，通常比一开始追求全面多云更清晰。

## 十六、AI 工作负载，让云上的几个老问题更加突出

模型推理和训练让 GPU 调度、数据传输与费用变得更显眼。云上能申请资源，不表示目标区域随时都有所需型号和配额。

推理服务要区分吞吐量、首字延迟、生成速度和总请求延迟。为了提高 GPU 利用率而增加批处理，可能会延长单个用户的等待，需要结合交互体验权衡。

如果使用外部模型 API，则要管理配额、并发、费用、数据发送范围和供应商故障。模型接口可用，也不代表输出质量符合要求，仍需要评测和业务兜底。

训练数据、向量索引、对象存储和计算实例之间的摆放，会直接影响搬运时间和传输费用。必要时将计算靠近数据，比反复传输大文件更有效。

这并没有改变云架构的基本逻辑：明确数据归属，限制资源消耗，记录可恢复状态，验证用户结果。只是资源变贵、输出更不确定之后，忽略这些问题的代价更高。

## 十七、从小项目到业务系统，可以分四步走

**第一步，部署得出来，也重建得出来。** 使用熟悉的计算平台、托管数据库和对象存储；建立自动构建、配置管理、TLS 和基本权限。不要把唯一数据放在应用临时目录。

**第二步，出了问题能够定位和恢复。** 建立业务指标、结构化日志、备份和实际恢复演练。先把恢复过程走通，再讨论更复杂的容灾目标。

**第三步，按真实风险补齐可用性。** 根据目标配置多实例、多可用区和数据库故障切换，检查所有关键依赖，测试超时、重复、断连和缩容。

**第四步，规模起来后再标准化。** 工作负载与团队多了，再投入平台工程、统一交付、自动扩缩和更精细的成本管理。每增加一层，都有明确负责人和运行规则。

这四步不是必须按日期完成的项目计划。关键是每一步都能留下可验证的能力，而不只是多一张架构图。

## 十八、上线前，可以用这些问题检查方案

下面的问题没有要求所有项目都回答“是”，但应该有人知道答案。

| 问题 | 它在检查什么 |
| --- | --- |
| 一个应用实例突然消失，正在处理的请求怎么办？ | 状态持久化、幂等与请求重试 |
| 一个可用区故障，还能完成哪些业务？ | 真实故障域与依赖分布 |
| 数据库被误删十万行，能恢复到哪里？ | 备份、时间点恢复、RPO 和验证流程 |
| 流量突然增加十倍，最先耗尽什么？ | 连接、配额、并发与准入控制 |
| 某个服务凭证泄露，能访问哪些资源？ | 最小权限和身份隔离 |
| 账单今天涨了三倍，多久能发现？ | 成本归属、提醒和异常分析 |
| 新版本失败，代码和数据分别怎样处理？ | 发布兼容、回退与补偿 |
| 离开当前厂商，需要迁移哪些数据和语义？ | 退出成本与架构边界 |

能回答这些问题，通常比使用了多少云产品更能说明方案是否成熟。

云平台把很多过去难以获得的能力变成了服务，但它不会替我们决定什么可以丢、什么必须保留，也不会替我们判断一次业务操作到底算不算成功。

可靠的云上系统，来自对责任、依赖、故障和成本的具体理解。把这些关系看清之后，云就不再是一堆产品名称，而是一组可以按需求组合、也必须按边界使用的工程能力。

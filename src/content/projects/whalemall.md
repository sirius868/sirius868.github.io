WhaleMall 是一个 Java 电商后端项目，涵盖商品、会员、购物车和订单等业务。我主要围绕两类问题推进它：普通订单如何在并发下正确处理库存与支付，以及限时购如何先挡住超额请求、最终又让数据库对结果负责。

## 订单与库存：先占住，再结算

下单不能只读取当前库存，再把计算结果写回去。两个请求可能同时看到同一个可用数量，都以为自己可以买。项目通过数据库条件更新预占库存，并让订单、订单项和预占操作处在同一个事务里；其中一步失败，前面的预占也会回滚。

库存分为实际数量和待付款订单的预占数量。支付成功时结算预占，取消时释放预占。这样可以明确区分“已经卖出”和“暂时留给待付款订单”的商品。

## 支付与取消：只允许一个结果生效

同一笔待付款订单，可能同时收到用户取消、超时取消和支付确认。项目用订单状态的条件转换决定哪条路径取得处理资格；只有转换成功的事务才能继续结算或释放库存。重复请求不会再次修改库存。任一库存更新失败，订单状态也会随事务回滚。

超时处理使用延迟取消消息，并用定时扫描兜底。两者最终进入同一取消路径，避免各自实现一套不同的库存规则。这里的重点是让状态和库存保持一致，而不是假设消息只会送达一次。

## 支付通知：核对来源，也保留异常痕迹

支付回调需要核验签名、应用和商户身份、订单号、金额及交易状态。有效通知可能重复，也可能在订单关闭后才到达。项目按交易号记录处理结果，区分已完成、迟到和冲突交易；主动查询支付状态只用于核对，不直接把订单改成已支付。

这条链路仍有明确边界：目前有模拟验签和数据库事务测试，尚无真实支付宝沙箱验签记录，因此不能把它描述成已经完成真实支付平台联调。

## 限时购：Redis 快速预占，MySQL 最终裁决

限时购请求容易在很短时间内集中到同一件商品。如果每个请求都直接进入数据库争抢名额，系统会承受大量注定失败的事务。项目在普通下单入口增加可选的活动关联参数：不传时仍走普通订单；传入时只允许购物车中的一个 SKU、一件商品，价格由服务端读取，也不能叠加优惠券或积分。

请求先通过 Redis Lua 检查活动名额和会员的临时预占，快速拒绝重复请求或已售罄请求。但 Redis 的计数不是最终订单数：随后仍由 MySQL 条件更新核对活动状态、时间、价格和名额，并用唯一约束保证同一会员对同一活动商品只生成一单。普通 SKU 库存也在同一个数据库事务中预占。这样，即使 Redis 快照过期或短暂失准，最终仍由数据库决定能否提交订单。

临时预占最难的是失败后如何回补。请求带有独立标记，Redis 名额快照带有版本；事务回滚时只回补属于同一标记、同一快照的名额，不把旧请求的名额加进后来重建的新快照。取消成功后，数据库释放库存与活动名额，再让 Redis 快照失效。支付、用户取消、超时扫描和消息取消仍使用互斥的订单状态转换，避免重复结算或释放。

这条链路已在独立 MySQL 和 Redis 下验证名额竞争、回滚、请求中断后临时标记过期、活动中途改价或下线，以及支付与取消竞争；也在隔离容器里通过真实 HTTP 走通限时购下单、取消和受控模拟支付。Redis 不可用时限时购请求会失败；临时预占可能导致短时间少卖，尚不能据此声称具备生产环境的高并发容量。

## 品牌详情：用两级缓存服务读多写少的页面

品牌详情先查 Caffeine 本地缓存，再查 Redis，最后回到 MySQL。后台更新品牌后清理 Redis；本地缓存设置较短过期时间，允许短时间的数据陈旧。订单库存、支付状态这类要求更严格的数据不使用这套本地缓存。

近期还在本地验证缓存重建锁：当多个独立本地缓存同时未命中时，用 Redis 短期锁协调回源，获锁后再次检查共享缓存，等待者在限定时间内重试；释放锁时核对持有者标记，避免旧请求误删新锁。真实 Redis 与多个独立缓存对象的专项测试已通过，但这批改动仍在 WhaleMall 的未提交工作区中，也还没有多 JVM、完整 HTTP 与 MySQL 链路的验证，因此不把它写成已发布的跨实例能力。

在重建锁改动之前的本机单实例热缓存测试中，品牌详情接口在 16 并发、三轮各 30 秒下，成功 QPS 中位数约 1718，P95 中位数约 13.69 毫秒，合计 152,711 次请求零错误。这个历史样本没有同条件的无缓存基线，也没有测重建锁改动后的表现，不能据此计算缓存带来的性能提升。

## 验证与当前边界

普通订单、支付、会员地址迁移和早期品牌缓存的历史回归为 46/46 通过。加入限时购及恢复场景后，`mall-portal` 的订单、支付、地址和限时购合并回归为 53/53 通过；运营端活动缓存失效另有 2/2 的测试记录。这些是不同清单，不能相加成一个“总测试数”，也不等于 53 条真实 HTTP 路径。

真实 HTTP 演练分别覆盖普通下单与受控模拟支付，以及限时购下单、用户取消和受控模拟支付。限时购还有隔离环境下的故障注入与只读对账、受控修复验证；目前没有远程 CI 通过记录。

目前验证重点是普通订单、限时购和品牌详情读接口。真实支付宝沙箱通知、RabbitMQ 到期投递的端到端验证、完整前端、长时间压测和生产部署仍不在已验证范围内。这个项目最值得复盘的，是把“并发下只处理一次”和“每个结果有证据可查”落实到实际业务链路中。
